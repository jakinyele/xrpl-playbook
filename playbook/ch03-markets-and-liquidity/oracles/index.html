    On-Ledger Price Oracles

    Why does this matter?

    XRPL price oracles are on-ledger objects that aggregate off-chain price feeds into a canonical source a smart-contract-equivalent (or any RPC consumer) can query. Unlike off-chain oracle services, an on-ledger oracle is immutable per ledger close, auditable by anyone, and subject to XRPL's finality guarantees. Understanding staleness, aggregation methodology, and trust assumptions is critical before using oracle prices in any financial logic.

    Mental model

    An oracle is a PriceOracle ledger object owned by an account (the oracle provider). Multiple oracle objects for the same asset pair exist independently; consumers use the get_aggregate_price RPC to aggregate across a set of trusted oracles using median, trimmed-mean, or other methods.

    Key insight: the XRPL oracle is a data availability layer, not a trust layer. The ledger enforces that the data came from the account that signed the PriceOracleSet transaction, but it does not validate that the price is correct. Consumers must apply their own trust model (e.g., trust N of M known providers).

    Architecture

    PriceOracle ledger object structure

    Field Type Description
    sfProvider STBlob Human-readable provider name (e.g., "Chainlink")
    sfAssetClass STBlob Asset class tag (e.g., "currency")
    sfPriceDataSeries STArray Array of {BaseAsset, QuoteAsset, AssetPrice, Scale}
    sfLastUpdateTime UINT32 Unix timestamp of last update
    sfExpiration UINT32 Optional; price is stale after this time

    AssetPrice is stored as a UINT64 integer; the actual price is AssetPrice × 10^(-Scale). Example: AssetPrice=17500, Scale=2 → 175.00.

    Source: rippled/src/libxrpl/tx/transactors/oracle/OracleSet.cpp

    get_aggregate_price RPC

    {
  "command": "get_aggregate_price",
  "base_asset": "XRP",
  "quote_asset": { "currency": "USD", "issuer": "<issuer>" },
  "oracles": [
    { "account": "<provider1>", "oracle_document_id": 1 },
    { "account": "<provider2>", "oracle_document_id": 1 }
  ],
  "trim": 20
}

    Response includes: - entire_set.mean, entire_set.std_dev, entire_set.size - trimmed_set.mean, trimmed_set.std_dev, trimmed_set.size - time (median LastUpdateTime across oracles)

    The trim parameter (0–25) removes the top and bottom trim% of prices before computing the mean — reducing manipulation via outlier submissions.

    Example flow

    Publish a price feed (provider role)

    1. Oracle provider account submits PriceOracleSet: 
      {
  "TransactionType": "OracleSet",
  "Account": "<provider>",
  "OracleDocumentID": 1,
  "Provider": "MyFeed",
  "AssetClass": "currency",
  "PriceDataSeries": [
    { "PriceData": {
        "BaseAsset": "XRP",
        "QuoteAsset": { "currency": "USD", "issuer": "<issuer>" },
        "AssetPrice": 17500,
        "Scale": 2
    }}
  ],
  "LastUpdateTime": <unix_timestamp>
}
    2. Oracle object is created (or updated) on-ledger.
    3. Provider repeats with each new price; the ledger stores only the latest value for each (Account, OracleDocumentID) pair.

    Consume a price feed (consumer role)

    1. Call get_aggregate_price with the set of trusted oracle accounts.
    2. Inspect trimmed_set.mean for the consensus price.
    3. Check time vs current ledger close time — if |time - now| > threshold, treat the price as stale and reject.
    4. Apply your application's business logic with the validated price.

    Source: rippled/src/libxrpl/tx/transactors/oracle/OracleSet.cpp Activation: PriceOracle amendment, 2024-11-02.

    Try it yourself

    Using the Testnet faucet at https://xrpl.org/resources/dev-tools/xrp-faucets:

    1. Submit a PriceOracleSet with a synthetic XRP/USD price. Then call get_aggregate_price and verify your price appears in the result.
    2. Submit two oracle providers with different prices. Observe how the mean and std_dev are computed. Then set trim=25 and verify the trimmed result.
    3. Delete one oracle with OracleDelete and re-run get_aggregate_price. How does the result change?
    4. Set Expiration to a past timestamp and observe what happens when consumers call get_aggregate_price after expiry.

    Security considerations

    • Staleness is your responsibility. The ledger does not enforce that prices are fresh. The LastUpdateTime field is set by the provider; if the provider stops updating, the price will be stale indefinitely unless Expiration is set.
    • Trust model is off-chain. The ledger validates that the provider signed the transaction, but not that the provider's price is accurate. Evaluate oracle provider reputation, SLA, and dispute history off-chain.
    • Outlier manipulation. A single oracle provider submitting a wildly wrong price can skew the mean. Use trim (e.g., 20–25%) and require a minimum quorum (e.g., oracles.size >= 5) before accepting the aggregate.
    • OracleDelete removes the object. If a provider deletes their oracle object, your get_aggregate_price call will silently include one fewer oracle. Monitor provider count in responses.

    Common mistakes

    • Not checking LastUpdateTime. Consumers that trust the ledger's get_aggregate_price result without checking time against the current ledger close time will use stale prices during provider downtime.
    • Using a single oracle. Relying on one provider makes you vulnerable to that provider's errors, downtime, or malicious behavior. Use a minimum of 3.
    • Ignoring Scale. AssetPrice=17500 with Scale=2 is $175.00, not $17500. Always apply the scale factor before comparing prices.
    • Treating oracle price as exact. The aggregate price has a std_dev. High std_dev signals disagreement across providers — widen your slippage tolerance or pause automated execution.

    Production checklist

    • [ ] Monitor LastUpdateTime on each oracle; alert if > freshness threshold.
    • [ ] Require a minimum quorum of oracles (e.g., ≥ 3) before executing.
    • [ ] Use trim=20 or higher to reduce outlier impact.
    • [ ] Monitor trimmed_set.size — if it drops below quorum, pause.
    • [ ] Implement circuit-breaker: if std_dev / mean > 5%, reject the aggregate.
    • [ ] Test with PriceOracle amendment on Testnet before Mainnet deployment.

    What I learned

    • On-ledger oracles solve the finality problem. Off-chain oracle requests race against ledger closes. An on-ledger oracle price is fixed for the entire ledger close — every transaction in that ledger sees the same price. No race conditions.
    • The provider account IS the oracle's trust anchor. If the provider account is compromised, its price submissions are indistinguishable from legitimate ones. Monitor the provider's signing key health.
    • get_aggregate_price is server-side computation. The aggregation is computed by the node, not consensus. Different nodes may return slightly different results if they have different oracle objects cached. Use a trusted, self-operated node for financial decisions.

    Open questions

    • Can oracle providers be permissioned? Currently any account can create an oracle object. An application-level allowlist of trusted provider accounts is needed to prevent oracle injection attacks.
    • What is the update frequency limit? PriceOracleSet costs a standard fee and is subject to normal rate limiting. For high-frequency feeds, evaluate whether XRPL on-ledger oracles provide sufficient freshness.
