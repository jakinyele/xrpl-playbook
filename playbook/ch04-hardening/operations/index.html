    Operations

    Why does this matter?

    Account security keeps your keys safe; node operations keep your service running. An xrpld node that falls behind the protocol, runs out of disk, or is blindsided by an amendment activation becomes an availability risk that no amount of key management can fix. Production systems need both disciplines.

    Mental model

    Think of a running xrpld node as a protocol participant that must satisfy three invariants simultaneously:

    1. Software currency — the node understands every amendment the network has activated. A node that doesn't is amendment-blocked and stops processing.
    2. Storage bound — ledger and transaction history grows without limit unless online deletion is configured. Unbounded growth ends in a forced outage.
    3. Read-path redundancy — a single node is a single point of failure. Any application that trusts one node exclusively inherits its availability budget.

    Architecture

    • Amendment lifecycle. A ledger-rule change is proposed by validators and tracked in-ledger via pseudo-transactions. It activates only after ≥ 80% validator approval sustained for two consecutive weeks. Activation is irreversible — there is no disable/rollback path. A server that does not understand an enabled amendment cannot operate on that ledger: it becomes amendment-blocked and halts validation.
    • SHAMapStore / online delete. xrpld stores ledger objects and transaction history in a key-value store (NuDB or RocksDB). Without pruning, this grows indefinitely. The online-delete mechanism uses two rotating databases (writable
    • recent-archival); on each rotation the older archive is dropped atomically. Configured in rippled.cfg under [node_db]:
    • online_delete — number of ledgers between deletion cycles.
    • advisory_delete — if 1, deletion only runs when triggered via the can_delete RPC; useful for coordinating pruning across a cluster.
    • Node topology. Production read paths should use at least two nodes behind a load balancer or with automatic failover. Validator nodes (if any) should be peered through a stock (non-validator) relay node to avoid exposing the validator IP.

    Example flow

    Surviving an amendment activation

    The failure mode this runbook prevents: an amendment your xrpld build does not understand reaches its activation threshold, the network enables it, and your node becomes amendment-blocked and stops processing. Because activation is irreversible, the only remedy is to upgrade before the deadline.

    1. Monitor the vote. Poll the feature RPC on a node you operate. With no feature parameter it returns the full amendment table under features; each amendment the network has seen reach majority carries a majority field — a timestamp of when it first held majority. That timestamp plus the two-week window (kDefaultAmendmentMajorityTime = weeks{2}) is the earliest possible activation time. Alert when any amendment your current build does not support gains a majority timestamp.
    2. Confirm you don't support it. An amendment with a majority timestamp that is not in your build's supported set is the one that will block you. Cross-check the amendment ID against your xrpld version's release notes.
    3. Upgrade before the deadline. Install the xrpld release that supports the pending amendment, on Testnet first, then on each production node. You have until majority + 2 weeks — but the majority can be lost and regained, which resets the clock, so treat the first majority timestamp as the hard deadline and upgrade well ahead of it.
    4. Verify not amendment-blocked. After upgrading, call server_info. A healthy node omits the amendment_blocked field entirely; the node only sets amendment_blocked: true when it is actually blocked. Also confirm complete_ledgers is advancing and the node is full/proposing as expected. Only then consider the upgrade complete.

    Why timing is the whole game: the 80% threshold (kAmendmentMajorityCalcThreshold = 80/100) and the two-week hold are the only warning you get, and there is no rollback once an amendment enables. A node that misses the window returns stale validated data silently until it is upgraded — so the monitoring in step 1 is not optional instrumentation, it is the control that keeps the service available.

    Security considerations

    • An amendment-blocked node returns stale ledger data silently; downstream services may not detect the staleness until reconciliation fails.
    • Online delete with advisory_delete = 1 requires an operator-triggered RPC; forgetting to trigger it means the older archive is never pruned — verify the delete cycle is automated or monitored.
    • Exposing a validator's public IP directly allows targeted DoS; relay through a stock node and keep the validator's peer list private.

    Common mistakes

    • Running a stale xrpld and ignoring amendment votes. An amendment that reaches its two-week threshold will activate and amendment-block the node, with no warning beyond the vote tracking data.
    • Disabling online delete (or leaving it unconfigured). Disk fills silently until the node halts and the service goes dark.
    • Depending on a single self-hosted node without failover. Any planned or unplanned restart takes the dependent application offline with it.
    • Not testing the upgrade path on Testnet first. xrpld upgrades that coincide with amendment activations can have ordering requirements; validate on Testnet before production.

    Production checklist

    • [ ] xrpld version is current; subscribe to release notifications.
    • [ ] Amendment voting status is monitored; alert fires ≥ 3 days before any amendment reaches its two-week activation threshold.
    • [ ] Online delete (online_delete) is configured in [node_db]; if advisory_delete = 1, the RPC trigger is automated and monitored.
    • [ ] Disk usage alerting is active with headroom ≥ 2× one deletion cycle.
    • [ ] At least two nodes are in the application read path with automatic failover; no single node is a hard dependency.
    • [ ] Validator (if any) is peered only through stock relay nodes; validator IP is not publicly exposed.
    • [ ] xrpld upgrade procedure is documented and has been tested on Testnet.
    • [ ] Node restart runbook exists; RTO target is defined and has been drilled.

    This is the node-operations baseline for every deployment. It complements the domain checklists in ch01 payments, ch02 issuer-controls / stablecoins / tokenization, and ch03 defi, plus the security checklist.

    What I learned

    • Amendment activation is a deadline, not an event you react to. The only warning is the majority timestamp exposed by the feature RPC plus the two-week hold. Because activation is irreversible and a blocked node fails silently, monitoring the vote is the load-bearing control — everything else in the runbook is downstream of catching the majority early.
    • The two-week window is a default, not a constant. amendmentMajorityTime is configurable (down to a 15-minute floor) and defaults to weeks{2}. On mainnet it is two weeks, but test networks may differ — never hard-code the deadline; read it from the network you are actually operating on.
    • A healthy node says nothing about being blocked. server_info only emits amendment_blocked when the node is blocked; the absence of the field is the success signal. Alerting must treat "field present and true" as the failure, not expect a "false".
    • Storage and amendments are the two silent killers. Both online-delete misconfiguration and a missed amendment fail quietly — the node keeps answering with stale or soon-to-halt state — which is why both belong in the same operational discipline rather than being treated as unrelated concerns.

    Open questions

    How far ahead of the activation deadline should an upgrade be scheduled?

    Educated guess (operational best practice, not protocol-enforced): treat the first majority timestamp as the deadline and aim to upgrade within a few days of it, not near the two-week edge. The majority can be lost and regained — which resets the clock — so the true activation time can only slip later, never earlier; upgrading early is therefore always safe. Testing on Testnet first (where the amendment typically activates ahead of mainnet) gives a rehearsal of the exact upgrade before it matters in production.

    Can online deletion and a missed amendment interact to cause data loss?

    Confirmed against source (mechanics) + educated guess (operational risk): online delete rotates two databases and drops the older archive atomically, so pruning itself is safe. The risk is procedural: an amendment-blocked node that is also still pruning can discard history it will need after the upgrade to resync cleanly. The conservative posture is to pause advisory_delete-driven pruning (stop triggering can_delete) once a node is known to be blocked, until it is upgraded and caught up.
