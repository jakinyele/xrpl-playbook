    Security

    Why does this matter?

    On the XRPL there is no "undo." A signed transaction that reaches a validated ledger is final — lost keys mean lost funds, and misconfigured accounts can permanently lock assets. Security is not a layer added on top of the design; it is baked into the account and signing architecture from day one.

    Mental model

    Think in layers of signing authority:

    1. Master key — unconditional authority over the account. Treat it like a root CA private key: generate it offline, use it once to configure the account, then disable it.
    2. Regular key — a delegated signing key. Rotate without touching the master key. Revoke without losing the account.
    3. Signer list (multi-signing) — M-of-N authorization. Required for any account where a single key compromise must not be catastrophic.

    Every operational account should have the master key disabled and use either a regular key, multi-signing, or both.

    Key type selection. Choose between secp256k1 (standard) and Ed25519 (modern) based on your hardware/HSM requirements. See Mental Models for the underlying math.

    • Issuing / cold accounts — air-gapped, master key disabled, multi- signing only. Signs the minimum necessary: configuration, issuance, emergency freeze.
    • Hot / operational accounts — regular key or HSM-backed signing; multi-signing for high-value thresholds. Signs day-to-day transactions.
    • Monitoring account — subscribes to the account's transaction stream; triggers alerting and incident response workflows.
    • Key ceremony — documented, auditable procedure for generating and distributing master and signer keys.

    Signing environments and codec safety. When an HSM or air-gapped machine signs transactions, it must serialize fields in exactly the same order and encoding the live network expects. Pin the serialization codec using server_definitions and verify the definitions_hash before every signing session — a hash mismatch means an amendment has shipped new field definitions and the offline signer must refresh before proceeding. See Custody for the full workflow.

    Node-level hardening (amendments, online delete, topology) is covered in the companion Operations section.

    Example flow

    Rotating a compromised regular key

    This runbook assumes the recommended posture: the account's master key is disabled (lsfDisableMaster) and day-to-day signing uses a regular key, with a signer list as the independent backstop. That backstop is what makes rotation safe — the protocol refuses to strand an account.

    1. Detect. Monitoring (see the account transaction stream in Architecture) flags anomalous activity signed by the current regular key. Treat the regular key as compromised and freeze outbound automation.
    2. Rotate via multi-sign. Because the master key is disabled, you cannot sign with it. Instead, submit a SetRegularKey transaction naming a freshly generated key in sfRegularKey, and authorize it with the signer list (M-of-N), not the compromised key. Two protocol rules matter here:
    3. The new regular key cannot equal the account address itself — SetRegularKey rejects that with temBAD_REGKEY (preflight).
    4. The first SetRegularKey an account submits for itself can be fee-free (the lsfPasswordSpent one-shot), but a multi-signed rotation is a normal fee-bearing transaction — budget the fee.
    5. Verify. Read the AccountRoot back and confirm sfRegularKey is the new key. Send a low-value test transaction signed by the new regular key and confirm it validates; attempt one signed by the old key and confirm it now fails authorization. Only then re-enable automation.
    6. Revoke (implicit) / de-provision. Assigning a new sfRegularKey in step 2 replaces the old one — there is only ever one regular key, so the compromised key is revoked the moment the rotation validates. Destroy the old key material and rotate any secrets that referenced it.

    Why the account can never be stranded: if you ever try to remove the regular key (a SetRegularKey with no sfRegularKey field) while the master key is disabled and no signer list exists, the transaction returns tecNO_ALTERNATIVE_KEY — the ledger will not leave an account with no usable signing method. Likewise, disabling the master key in the first place (asfDisableMaster) requires that a regular key or signer list already exist, and must itself be signed by the master key (tecNEED_MASTER_KEY / tecNO_ALTERNATIVE_KEY). Keep the signer list independent of the regular key's infrastructure so a single compromise never takes out both.

    Security considerations

    • DepositAuth requires the account to explicitly authorize incoming payments; prevents unsolicited asset delivery.
    • DisallowIncoming flags block incoming trust lines, offers, and NFT offers — use on accounts that should not receive unsolicited objects.
    • Tickets allow pre-authorizing transactions at a known sequence; useful for queued multi-party signing workflows.
    • Fee escalation under load can cause legitimate transactions to expire; monitor fee levels and adjust transaction costs dynamically.

    Common mistakes

    • Leaving the master key active on operational accounts. A single key compromise yields full account control.
    • Insufficient signer quorum. A 1-of-3 signer list provides less security than it appears if signers share infrastructure.
    • No LastLedgerSequence on signed transactions. Transactions without an expiry can be applied to the ledger long after signing.
    • Hot wallet holds excessive XRP. Minimize funds on hot accounts; sweep regularly to cold storage.
    • No incident response runbook. The ledger is live 24/7; a compromised key at 3 AM requires a practiced response, not improvisation.

    Production checklist

    • [ ] Master key disabled on all operational accounts.
    • [ ] Multi-signing configured on issuing and high-value accounts.
    • [ ] Regular key rotation procedure is documented and tested.
    • [ ] DepositAuth enabled on accounts that should not receive unsolicited payments.
    • [ ] All submitted transactions include a valid LastLedgerSequence.
    • [ ] Hot wallet balances are minimized and swept on schedule.
    • [ ] Real-time monitoring and alerting is active on all operational accounts.
    • [ ] Incident response runbook exists, is versioned, and has been drilled.

    This is the account-security baseline for every deployment. It complements the domain checklists in ch01 payments, ch02 issuer-controls / stablecoins / tokenization, and ch03 defi, plus the operations checklist.

    What I learned

    • The protocol refuses to strand an account. Every path that would leave an account with no usable signing method is blocked: removing the regular key while the master is disabled and no signer list exists returns tecNO_ALTERNATIVE_KEY, and disabling the master key requires an alternative to already be in place. Key rotation is therefore safe by construction — but only if you set up the backstop (regular key and an independent signer list) before you disable the master.
    • Rotation is replacement, not addition. An account has exactly one regular key; assigning a new one via SetRegularKey atomically revokes the old one the moment the transaction validates. There is no window where two regular keys are valid, and no separate "revoke" transaction is needed.
    • Some actions are master-key-only, forever. asfNoFreeze (and disabling the master itself) must be signed by the master key. If you have already disabled the master, you can never set NoFreeze — so irreversible posture decisions have to be made during the initial key ceremony, not retrofitted.
    • The first regular-key set can be free, once. The lsfPasswordSpent one-shot lets a newly funded account self-assign a regular key without a fee, but it arms only once; every subsequent (and every multi-signed) rotation is a normal fee-bearing transaction.

    Open questions

    When should an account use a regular key versus a signer list versus both?

    A regular key is a single delegated signer — operationally simple, ideal for automated hot-path signing where one HSM or service holds the key. A signer list is M-of-N — it removes any single point of compromise but adds coordination cost per transaction. The recommended production posture uses both: the signer list is the high-assurance backstop (and the thing that makes disabling the master safe), while the regular key handles routine signing. Crucially, keep their infrastructure independent, so compromising the regular key never also yields a signer-list quorum. Confirmed against source — both are accepted alternatives to the master key in the disable-master guard (AccountSet.cpp) and the SetRegularKey.cpp removal check.

    What is the safe ordering of the initial key ceremony?

    Educated guess (operational best practice, not protocol-enforced): (1) fund the account; (2) install the signer list (SignerListSet); (3) install the regular key (SetRegularKey); (4) set any master-key-only irreversible flags you need (asfNoFreeze, etc.); (5) last, disable the master key (asfDisableMaster). The protocol enforces the individual dependencies (you cannot disable the master without an alternative, and NoFreeze needs the master), but the sequence that avoids ever being locked out is an application-level discipline.
