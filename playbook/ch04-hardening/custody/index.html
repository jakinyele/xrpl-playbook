    Custody

    Why does this matter?

    On the XRPL there is no undo. A transaction that reaches a validated ledger is final. For custodians — exchanges, institutional wallets, treasury systems — this means correctness must be guaranteed before a key signs anything.

    The core risk is codec drift: an offline signer (HSM, vault, air-gapped machine) that serializes a transaction using an outdated field definition produces bytes the network cannot verify. The signature will fail or, in a worse scenario, validate a different byte string than intended.

    The server_definitions RPC method is the protocol-level solution. It exposes the complete serialization codec as a single, hash-pinned JSON payload. Matching that hash across environments proves the codec is byte-identical and offline signing is safe.

    Mental model

    Two environments. One codec. The definitions_hash is the handshake.

    ┌─────────────────────────────┐       ┌───────────────────────────────┐
│  ONLINE ENVIRONMENT         │       │  AIR-GAPPED / HSM             │
│                             │       │                               │
│  Transaction builder        │──────▶│  Cached server_definitions    │
│  (constructs JSON fields)   │ hash  │  (field order, type codes,    │
│                             │ check │   signing-field flags)        │
│  server_definitions check   │       │                               │
│  (verifies hash matches)    │       │  Private key                  │
│                             │       │  (never leaves this env)      │
└─────────────────────────────┘       └───────────────────────────────┘
          │                                         │
          │         signed tx_blob                  │
          └─────────────────────────────────────────┘
                          │
                    submit RPC
                          │
                    xrpld node

    If the hashes match: the offline signer will produce byte-identical serialization to what the network expects. Sign.

    If the hashes diverge: an amendment has shipped new field definitions. Block signing. Alert operator. Refresh the cached codec before continuing.

    Architecture

    3-tier signing stack:

    sequenceDiagram
    participant B as Transaction Builder<br/>(online)
    participant G as Codec Gate<br/>(online boundary)
    participant S as Offline Signer<br/>(air-gapped / HSM)
    participant N as XRPL Node

    B->>N: server_definitions
    N-->>B: {FIELDS, TYPES, hash}
    B->>B: Build unsigned tx JSON<br/>(fee, sequence, LastLedgerSeq)

    B->>G: Forward tx JSON + expected hash
    G->>N: server_definitions (verify)
    N-->>G: {hash}

    alt Hash matches
        G->>S: tx JSON + cached definitions
        S->>S: Serialize with cached codec<br/>Sign → tx_blob
        S-->>G: tx_blob
        G->>N: submit tx_blob
        N-->>G: preliminary result
    else Hash mismatch
        G->>G: HALT — amendment detected<br/>Alert operator<br/>Refresh codec before retry
    end
    1. Transaction builder (online) — constructs the transaction JSON from business logic (amount, destination, fee from server_info, sequence from account_info, LastLedgerSequence from current ledger).
    2. Codec gate (online, boundary layer) — calls server_definitions with the cached hash. Match → forward to signer. Mismatch → halt and alert.
    3. Offline signer (air-gapped / HSM) — receives the transaction JSON, serializes using cached definitions, signs the hash, returns tx_blob.

    The private key never enters tier 1. The definitions JSON is not secret — it is publicly derivable from any xrpld node of the same version.

    server_definitions deep dive

    Handler: rippled/src/xrpld/rpc/handlers/server_info/ServerDefinitions.cpp Role: USER (no admin credentials required)

    Response structure

    Section Contents
    TYPES SerializedTypeID → name mapping (UInt32, Amount, AccountID, Blob, STObject, STArray, …)
    FIELDS Array of [name, {nth, isVLEncoded, isSerialized, isSigningField, type}] — the binary codec backbone
    TRANSACTION_TYPES Payment: 0, EscrowCreate: 1, AMMCreate: 80, …
    TRANSACTION_FORMATS Per-type required/optional field lists (the template for each tx)
    LEDGER_ENTRY_TYPES ltACCOUNT_ROOT, ltRIPPLE_STATE, ltAMM, ltMPTOKEN, …
    LEDGER_ENTRY_FORMATS Per-type required/optional field lists for ledger objects
    TRANSACTION_RESULTS Full TER taxonomy (tesSUCCESS: 0, tecUNFUNDED_PAYMENT: 101, …)
    TRANSACTION_FLAGS Per-type flag bitmasks (tfPartialPayment: 0x00020000, …)
    LEDGER_ENTRY_FLAGS Per-type ledger state flag bitmasks (lsfDisableMaster, …)
    ACCOUNT_SET_FLAGS asf* integer values for AccountSet operations
    hash SHA512Half(canonical_json_of_all_sections_above) — the codec fingerprint

    Hash computation (source-verified)

    // ServerDefinitions.cpp:361–366
std::string const out = json::FastWriter().write(defs_);
defsHash_ = xrpl::sha512Half(xrpl::Slice{out.data(), out.size()});
defs_[jss::hash] = to_string(defsHash_);

    The hash is computed once at server startup from the canonical JSON serialization of all sections. It is stable for the lifetime of the process and changes only when the xrpld version ships a new codec (typically via amendment activation).

    Bandwidth optimization

    The handler accepts an optional hash parameter:

    { "command": "server_definitions", "hash": "<your-cached-hash>" }
    • Hash matches → response is { "hash": "<hash>" } only (~60 bytes). Client already has the current codec; no re-download needed.
    • Hash missing or mismatch → full response (~100 KB JSON).

    Use this in the codec gate on every signing session: cheap confirmation that the codec has not changed, with automatic full refresh on divergence.

    Codec pinning workflow

    Setup (once per xrpld version)

    1. Call server_definitions (no hash param)
2. Receive full codec JSON
3. Compute: expected_hash = SHA512Half(canonical_json)
4. Assert: expected_hash == response.hash  ← verify no MITM/truncation
5. Store: (codec_json, hash) → HSM firmware / signing library config
6. Tag: firmware_version = xrpld_version_string

    Per-session codec gate (online, before each signing batch)

    1. Call server_definitions with { hash: cached_hash }
2. If response contains only "hash" field:
     → codec unchanged; proceed to signing
3. If response contains full definitions:
     → hash changed (amendment activated)
     → HALT: do not sign with stale codec
     → ALERT: operator must review new definitions and upgrade signing env
     → After upgrade: repeat Setup step

    Signing (offline / HSM)

    1. Receive transaction JSON from online builder
2. Validate all fields exist in cached TRANSACTION_FORMATS for this tx type
3. Sort fields by fieldCode = (type_id << 16) | field_index
4. Exclude fields where isSigningField = false (TxnSignature, Signers array)
5. Serialize each field per its type and isVLEncoded flag
6. Hash: signing_hash = SHA512Half(0x53545800 || serialized_bytes)
   (prefix 0x53545800 = "STX\0" — the transaction signing prefix)
7. Sign signing_hash with private key (RFC 6979 deterministic for secp256k1)
8. Encode signature as DER; enforce low-S (canonical signature)
9. Insert TxnSignature into tx, re-serialize full blob (now including sig field)
10. Return tx_blob (hex)

    Source refs: - Field metadata: FIELDS section of server_definitions - Signing prefix: rippled/include/xrpl/protocol/HashPrefix.h (transactionID) - Canonical low-S: rippled/src/libxrpl/protocol/SecretKey.cpp

    Amendment lifecycle for custody

    When an amendment activates, xrpld may add or reorder fields in the codec. The server_definitions hash changes at that moment.

    Risk without pinning: An HSM running old definitions serializes a transaction without a new required field (or with it in the wrong position). The live network deserializes different bytes than the HSM hashed → signature verification fails → transaction rejected with temINVALID.

    Safe upgrade path:

    1. Monitor: amendment reaches 80% support (alert from operations runbook)
2. Pre-upgrade: fetch new server_definitions from a Testnet/Devnet node
   running the new version → test signing against it
3. Activation: amendment goes live on Mainnet (hash changes on live nodes)
4. Codec gate detects mismatch → signing halted automatically
5. Deploy: update HSM firmware / signing library with new definitions
6. Resume: codec gate confirms new hash → signing resumes

    Testnet typically activates amendments before Mainnet. Use it to rehearse the codec upgrade before the Mainnet hash changes.

    See also: Operations → Amendment monitoring.

    Try it yourself

    Using the Testnet faucet at https://xrpl.org/resources/dev-tools/xrp-faucets:

    1. Run examples/05-offline-signing/ — trace each tier. What does the server_definitions hash look like? How long is it (bytes)?
    2. Deliberately corrupt the transaction blob before submission (flip one hex character). What error does the node return? Is it a tem* or something else?
    3. Simulate a codec mismatch by hardcoding a wrong pinnedHash in the offline-sign script. Does the gate correctly refuse to sign?
    4. Compare server_definitions hashes between two different Testnet nodes. Are they identical? What does it mean if they differ?
    5. Sign a transaction with a future Sequence (current + 10). Submit it. What happens? Can you submit the gap transactions to make it validate later?

    Security considerations

    • Codec JSON is not a secret. Any xrpld node of the same version returns identical definitions. Protect the private key, not the definitions.
    • Codec injection. If the online codec gate is compromised, an attacker could serve a modified definitions payload that maps fields to different byte positions — causing the HSM to sign bytes the network interprets differently. Mitigate: verify the hash locally against a trusted node and a pinned known-good hash from the signing library vendor.
    • Library pinning. Client libraries (xrpl.js, xrpl-py) bundle their own copy of server_definitions. Pin the library version alongside the xrpld version. A library upgrade may ship updated definitions — verify the embedded hash matches the live network before deploying.
    • Multi-sig and codec. Each co-signer in an M-of-N setup must use the same codec. Staggered HSM upgrades can cause co-signers to produce signatures over different byte representations of the same transaction. Upgrade all co-signers atomically, or collect all signatures before switching any node.
    • Key material isolation. The private key must never transit the online environment. The definitions JSON (not secret) flows online → offline. The tx_blob (signed, public) flows offline → online. Nothing else crosses.

    Common mistakes

    • Signing without a codec gate. Using a hard-coded or bundled codec without verifying against the live network. Silent until an amendment ships; then all signatures fail.
    • Comparing library version instead of hash. A library patch release can ship updated definitions. Always compare hashes, not version strings.
    • Forgetting the signing prefix. The bytes signed are SHA512Half(0x53545800 || serialized_tx), not SHA512Half(serialized_tx). Signing the wrong preimage produces a valid-looking but unverifiable signature.
    • Including TxnSignature in the signing payload. isSigningField = false for TxnSignature. Including it produces a circular dependency. The field is inserted after signing, not before.
    • Staggered co-signer upgrades. In multi-sig setups, upgrading one HSM before others causes codec mismatch between co-signers. Signatures over different byte representations do not combine — the transaction is rejected.
    • Not testing on Devnet/Testnet first. Amendments activate on Testnet before Mainnet. The codec upgrade drill should always run on Testnet first.

    Production checklist

    • [ ] server_definitions hash verified against live node before every signing session; mismatch halts signing and pages on-call.
    • [ ] Cached definitions stored with the xrpld version tag they were fetched from.
    • [ ] Signing library (xrpl.js / xrpl-py) version pinned; embedded definitions hash confirmed to match live network hash.
    • [ ] Amendment monitoring alert fires when any pending amendment reaches ≥ 70% support for one week (gives one week before activation).
    • [ ] Codec upgrade runbook written and rehearsed on Devnet/Testnet.
    • [ ] Multi-sig co-signers have a coordinated upgrade plan; no staggered HSM firmware deployments across a signing quorum.
    • [ ] Signing prefix (0x53545800) and low-S enforcement verified in signing library test suite.
    • [ ] TxnSignature and Signers excluded from signing payload (confirmed via isSigningField = false in definitions).
    • [ ] Submitted tx_blob round-tripped: decode and compare field-by-field against original transaction JSON before broadcasting.
    • [ ] Key material never transits the online environment; only tx_blob (public) crosses the boundary from offline to online.

    What I learned

    • The hash is the handshake, not the payload. The definitions JSON is large (~100 KB) but changes rarely. The hash check is cheap (one RPC, tiny response when cached). Build the codec gate around the hash check, not a full re-download every session.
    • isSigningField is the serialization boundary between construction and signing. Understanding which fields are excluded (signature, multi-sig array) clarifies why offline signers need the full field metadata, not just the field names.
    • Testnet is the amendment rehearsal environment. The two-week majority window on Mainnet almost always follows an earlier Testnet activation. The codec upgrade drill should be a standard part of the Testnet runbook, not an emergency response to Mainnet activation.

    Open questions

    • Will a future server_info response embed the definitions_hash inline, eliminating the need for a separate server_definitions round-trip in the codec gate?
    • How should a custody system handle an xrpld node that is running a version ahead of the HSM's pinned codec (e.g., a node upgraded before the amendment activated, serving updated definitions before the network hash changes)?
