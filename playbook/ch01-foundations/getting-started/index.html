    Getting Started

    Why does this matter?

    Every other section in this playbook explains what the ledger does and why. This section is where you make it run. The goal is a working loop — connect → fund → build → sign → submit → confirm — that you can reuse for every transaction type in later chapters. Getting this loop right once means you never again confuse a preliminary engine result with a validated outcome, and you have a safe, retryable submission pattern from the first line of code.

    You will also stand up a local standalone node, which is the sandbox the ch06 amendment worked example depends on: a private network where you control consensus and can advance ledgers on demand.

    Mental model

    Two facts drive everything here, both established in Mental Models:

    1. Finality is deterministic. There is no "confirmation depth" to tune. A transaction is either in a validated ledger or it is not. So the only thing your submission code waits for is the validated flag — not a block count.
    2. A preliminary result is a prediction. The engine result you get back at submission time (e.g. tesSUCCESS) reflects how one node would apply the transaction to its current open ledger. The authoritative result comes only from the validated ledger. This is why you use submitAndWait / submit_and_wait rather than a bare submit.

    The reliable-submission contract is: bind the transaction to an expiry (LastLedgerSequence) so that if it does not make it into a ledger by then, it can never apply later — which makes a rebuild-and-retry safe. The official SDKs enforce this: submitAndWait in xrpl.js throws if the transaction has no LastLedgerSequence, and autofill sets a sensible default for you.

    Architecture

    There are three moving parts:

    • A client library. xrpl.js (JavaScript/TypeScript) and xrpl-py (Python) are the two reference SDKs maintained by XRPLF. Both expose the same three primitives you need: a client (WebSocket or JSON-RPC), a Wallet (keys + address), and reliable submission (submitAndWait / submit_and_wait).
    • A network endpoint. For learning, use the public Testnet (wss://s.altnet.rippletest.net:51233 for WebSocket, https://s.altnet.rippletest.net:51234 for JSON-RPC) plus its faucet, which funds a fresh account for you. For deterministic testing, use your own standalone node (below).
    • Autofill. Fields that can be looked up (Fee, Sequence, LastLedgerSequence) are filled automatically by autofill — invoked for you inside submitAndWait / submit_and_wait when you pass an unsigned transaction and a wallet. Any field you set explicitly is not overridden.

    Your first transaction — JavaScript (xrpl.js)

    const { Client, Wallet } = require("xrpl");

async function main() {
  const client = new Client("wss://s.altnet.rippletest.net:51233");
  await client.connect();

  // Fund a fresh Testnet account from the faucet.
  // Returns { wallet, balance }; the faucet is auto-selected for the network.
  const { wallet } = await client.fundWallet();

  const prepared = await client.autofill({
    TransactionType: "Payment",
    Account: wallet.address,
    Destination: "rPT1Sjq2YGrBMTttX4GZHjKu9dyfzbpAYe",
    Amount: "1000000", // drops = 1 XRP
  });

  const signed = wallet.sign(prepared);

  // submitAndWait waits for a *validated* ledger, not just submission.
  const result = await client.submitAndWait(signed.tx_blob);

  // The authoritative result lives in the validated metadata.
  console.log("validated:", result.result.validated);
  console.log("engine result:", result.result.meta.TransactionResult);

  await client.disconnect();
}

main().catch(console.error);

    Your first transaction — Python (xrpl-py)

    from xrpl.clients import JsonRpcClient
from xrpl.models import Payment
from xrpl.transaction import submit_and_wait
from xrpl.utils import xrp_to_drops
from xrpl.wallet import generate_faucet_wallet

client = JsonRpcClient("https://s.altnet.rippletest.net:51234")

# Fund a fresh Testnet account from the faucet.
wallet = generate_faucet_wallet(client)

payment = Payment(
    account=wallet.address,
    destination="rPT1Sjq2YGrBMTttX4GZHjKu9dyfzbpAYe",
    amount=xrp_to_drops(1),
)

# Autofills (Fee/Sequence/LastLedgerSequence), signs, submits, and waits
# for a validated (or definitively failed) result.
response = submit_and_wait(payment, client, wallet)

print("validated:", response.result["validated"])
print("engine result:", response.result["meta"]["TransactionResult"])

    Both examples do the same thing: fund → build → autofill → sign → submit → wait for validation. Neither treats the preliminary engine result as final.

    Running a local standalone node

    A standalone node runs its own private ledger with no peers and no external consensus — you are the only validator, and you advance the ledger manually. This is the ideal sandbox for testing amendment activation (ch06), because you control which features are enabled and when ledgers close.

    Start xrpld with the -a (standalone) flag. Confirmed against source (Main.cpp): --standalone,-a runs "with no peers," --start starts "from a fresh Ledger," and --ledger loads a specific ledger.

    # Start a fresh standalone ledger with no peers.
xrpld -a --start

    In standalone mode the ledger does not close on a timer — nothing advances until you tell it to. Use the ledger_accept RPC (a standalone-only method, confirmed present in the RPC handlers) to close and validate the current open ledger:

    xrpld ledger_accept

    Each ledger_accept closes the open ledger, validates it, and opens the next one. This is what makes standalone deterministic: transactions apply exactly when you advance the ledger, so tests never race the 3–5 second close timer.

    Non-obvious insight: standalone mode is not just "Testnet on localhost." Because you are the sole validator, amendments you vote for reach the 80% threshold instantly on the next flag ledger — there is no two-week majority wait. That is precisely why it is the right tool for the ch06 amendment exercise. On a public network you cannot force activation; in standalone you can.

    Example flow

    Goal: send your first payment on Testnet and confirm it is validated.

    1. Connect. Instantiate a client against the Testnet endpoint and connect(). Use the WebSocket endpoint (:51233) if you want subscriptions; JSON-RPC (:51234) is fine for request/response.
    2. Fund. Call fundWallet() / generate_faucet_wallet(). The SDK picks the correct faucet for the connected network and returns a funded Wallet. The account now exists on-ledger with at least the base reserve.
    3. Build + autofill. Construct a Payment. autofill (run implicitly by submitAndWait / submit_and_wait) sets Fee from current load, Sequence from the account, and LastLedgerSequence as an expiry a few ledgers ahead.
    4. Sign + submit + wait. The reliable-submission method signs locally, broadcasts, and polls until the transaction is in a validated ledger or has definitively failed / expired.
    5. Read the authoritative result. Check result.validated === true and read meta.TransactionResult. For payments, read delivered_amount from metadata — never the request Amount (see Payments).
    6. (Optional) inspect it. Look the transaction hash up on the Testnet explorer to see the validated ledger it landed in.

    If you ran the same flow in standalone, step 4 would not complete on its own — you would call ledger_accept to close the ledger, and only then would the transaction become validated.

    Try it yourself

    Using the Testnet faucet at https://xrpl.org/resources/dev-tools/xrp-faucets:

    1. Run examples/01-connect-and-fund/ — check the Flags and OwnerCount on your newly funded account. What do each of those fields tell you?
    2. Run examples/02-reliable-submission/ — observe the polling cycle. What happens if you set SAFETY_WINDOW=1 (very short expiry)?
    3. Create a Ticket using TicketCreate with TicketCount=3. Then submit 3 transactions in reverse sequence order using TicketSequence. Do they all succeed? What does account_objects show after?
    4. Kill a running submission mid-poll and restart. Does the recovery logic correctly detect the already-validated transaction, or does it rebuild?
    5. Connect to a standalone node (ledger_accept to close ledgers manually). How does transaction validation behavior differ from Testnet?

    Security considerations

    • Faucet wallets are disposable. The keys returned by the faucet are for Testnet only. Never reuse a Testnet seed on Mainnet, and never commit any seed to source control.
    • Sign locally, not on a remote node. Both SDKs sign the transaction in your process; the node only receives the signed blob. Do not send seeds or secret keys to an RPC endpoint you do not control.
    • Always bind an expiry. Reliable submission depends on LastLedgerSequence. Without it, a transaction can linger and apply unexpectedly later — xrpl.js refuses to submitAndWait a transaction that lacks one. Do not disable this by hand-setting fields.
    • Treat the preliminary result as advisory. Do not update application state, release goods, or mark an invoice paid on the engine result alone. Wait for validated.

    Common mistakes

    • Treating tesSUCCESS at submission as final. It is a prediction from one node's open ledger. Use submitAndWait / submit_and_wait and check validated.
    • Reusing a stale Sequence on retry. If a transaction expired, rebuild it (fresh Sequence and LastLedgerSequence) rather than resubmitting the old blob. Let autofill refetch the sequence.
    • Forgetting the ledger does not advance in standalone. New users start xrpld -a, submit a transaction, and wait forever. You must call ledger_accept to close the ledger.
    • Reading Amount instead of delivered_amount. For anything other than a simple full XRP payment, the delivered amount can differ; read it from metadata.
    • Hard-coding a fee. Fees float with network load. Let autofill set the fee from server_info, or you risk telINSUF_FEE_P under load.

    Production checklist

    • [ ] Using a maintained SDK (xrpl.js or xrpl-py) rather than hand-rolling signing and serialization.
    • [ ] All submissions go through submitAndWait / submit_and_wait (or an equivalent that verifies validated).
    • [ ] Every transaction carries a LastLedgerSequence (rely on autofill).
    • [ ] Retry logic rebuilds expired transactions with a fresh sequence rather than resubmitting the old blob.
    • [ ] Fees are derived from current network load, not hard-coded.
    • [ ] Seeds/secret keys are held in a secret manager, never in source or logs.
    • [ ] Integration tests run against a standalone node (deterministic) before Testnet, and Testnet before Mainnet.

    What I learned

    • The submission loop is the same for every transaction type. Once connect → fund → autofill → sign → submitAndWait is muscle memory, every later chapter is just a different transaction body plugged into the same loop.
    • autofill is doing quiet correctness work. It is not a convenience — it is where Fee, Sequence, and the reliable-submission LastLedgerSequence come from. Bypassing it is how people reintroduce the bugs the SDK prevents.
    • Standalone mode is the highest-leverage learning tool. Deterministic ledger advancement (ledger_accept) and instant amendment activation make it faster and clearer than Testnet for understanding cause and effect.
    • The SDKs enforce the mental model. xrpl.js literally throws without a LastLedgerSequence; the "wait for validated" contract is baked into submitAndWait. The library refuses to let you make the classic finality mistake.

    Open questions

    What is the recommended pattern for high-throughput submission where a single account submits many transactions per second?

    Confirmed against source (rippled/src/libxrpl/tx/transactors/account/ TicketCreate.cpp, TicketBatch amendment — retired and core, meaning Tickets are always available): Because each transaction is valid at exactly one Sequence, naive parallel submission from one account serializes on the sequence number. The two correct production patterns are: 1. Sequential sequence-manager — a single goroutine/thread assigns and tracks sequences; submits in order with per-transaction LastLedgerSequence windows. Simple, predictable, low throughput ceiling. 2. Tickets (TicketCreate) — pre-reserve N sequence slots in a single on-ledger transaction; transactions referencing tickets can be built and submitted out of order without sequence conflicts. Each Ticket costs one sequence slot and 0.2 XRP reserve. Ideal for parallel, out-of-order submission (e.g., batch payouts, concurrent API calls).

    Source: TicketCreate.cpp preflight confirms a ticket consumes the ticketing account's OwnerCount and validates the TicketSequence field format.

    How should a service recover the definitive outcome of a transaction after a process crash mid-submission?

    Confirmed. The hash + LastLedgerSequence recovery pattern is the documented reliable-submission loop and is protocol-enforced. On restart: 1. Load the persisted signed tx hash and LastLedgerSequence (must be persisted before broadcast — write-ahead guarantee). 2. Query tx by hash against a validated-ledger node. 3. If validated=true → record outcome; done. 4. If current ledger index > LastLedgerSequence and not found → the tx can never apply; safe to increment sequence and rebuild. 5. If current ledger index ≤ LastLedgerSequence → resubmit the same blob (idempotent; duplicate submission returns tefALREADY if already included, or re-enters the queue if not).

    Source: rippled/include/xrpl/protocol/TER.h — tefALREADY (-168) prevents replay. See examples/02-reliable-submission/ for a runnable implementation.
