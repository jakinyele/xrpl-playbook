    Glossary and prefix conventions

    A single reference for the terminology and the naming prefixes used throughout this playbook. The XRPL source uses terse, systematic prefixes for result codes, flags, fields, ledger objects, and transaction types. Once you can decode a prefix, an unfamiliar identifier becomes largely self-documenting.

    Every prefix meaning here is anchored to the vendored rippled/ source.

    Result-code prefixes (TER family)

    Every transaction returns a result code. The two-and-a-bit-letter prefix tells you what class of outcome it is — and, critically, whether it reaches a validated ledger and whether a fee is charged. Source of truth: rippled/include/xrpl/protocol/TER.h (the code ranges and their comments).

    Prefix Class Code range Reaches a validated ledger? Fee charged? Meaning
    tes Success 0 (tesSUCCESS) Yes Yes The transaction succeeded.
    tec Claimed cost ≥ 100 Yes Yes Failed to achieve its effect, but was well-formed, so it claims the fee and consumes the sequence. "Claim fee to use the sequence number."
    ter Retry -99 .. -1 No No Could succeed in a later ledger (e.g. terQUEUED, terPRE_SEQ). May be held/forwarded.
    tef Failure -199 .. -100 No No Cannot succeed now (e.g. sequence already used, tefPAST_SEQ) but could in an imagined ledger.
    tem Malformed -299 .. -200 No No The transaction is invalid in any ledger (bad signature, bad amount). Never applies.
    tel Local error -399 .. -300 No No Rejected by this node's local policy (fee below load, telINSUF_FEE_P). Another node might accept it.

    Non-obvious insight (the line that matters most): only tes and tec ever appear in a validated ledger, and both charge a fee. Everything with a negative code (tel/tem/tef/ter) is rejected before it lands, so it costs nothing and does not consume the sequence number. This is the single most important thing a developer coming from a gas-metered chain must internalize: a malformed or premature transaction is free, and only a transaction that made it far enough to claim a sequence slot (tec) costs you the fee on failure. See ch01 transaction engine internals for why the pipeline enforces this.

    The helper predicates isTesSuccess, isTecClaim, isTerRetry, isTefFailure, isTemMalformed, and isTelLocal in TER.h implement exactly these range checks.

    Flag and field prefixes

    XRPL uses distinct prefixes for the different kinds of flags and identifiers. Confusing them is a common source of bugs — an asf* value is not interchangeable with a tf* value even when they concern the same setting.

    Prefix Kind Where set / stored Source
    tf Transaction flags — per-submission bits in the Flags field (e.g. tfPartialPayment, tfFullyCanonicalSig). Set on the transaction you submit. TxFlags.h
    asf AccountSet flags — enable/disable persistent account settings via AccountSet SetFlag/ClearFlag (e.g. asfRequireDest, asfDisableMaster, asfDefaultRipple). Passed as an integer to AccountSet. TxFlags.h
    lsf Ledger state flags — the stored bits that an asf* setting toggles, read back on the on-ledger object (e.g. lsfRequireAuth, lsfDisableMaster, lsfDefaultRipple). Read from AccountRoot / RippleState. LedgerFormats.h
    sf Serialized fields — the canonical named fields of every object/transaction (e.g. sfAccount, sfSequence, sfAmount). The serialization/type layer. SField / sfields.macro
    lt Ledger entry types — the kinds of on-ledger objects (e.g. ltACCOUNT_ROOT, ltRIPPLE_STATE, ltOFFER, ltAMM). Ledger object type tags. ledger_entries.macro
    tt Transaction types — the enumerated transaction kinds (e.g. ttPAYMENT, ttOFFER_CREATE, ttAMENDMENT). The TransactionType field. transactions.macro

    Watch out: asf* (the verb you send) and lsf* (the noun you read back) frequently describe the same setting under different names. For example, sending asfDefaultRipple sets the stored lsfDefaultRipple bit; sending asfDisableMaster sets lsfDisableMaster. When you submit, use asf*; when you inspect account state, expect lsf*.

    Core terms

    Term Definition
    Account An entry (ltACCOUNT_ROOT) identified by an r-address, holding the XRP balance, Sequence, flags, and owner count. Must be funded above the base reserve to exist.
    Amendment An on-ledger, vote-activated protocol change. Requires ~80% validator support sustained for two weeks. Permanent once activated. See ch06.
    Autofill SDK step that populates Fee, Sequence, and LastLedgerSequence before signing. See Getting Started.
    Base reserve The minimum XRP an account must hold to exist. A protocol-level, adjustable amount.
    Drops The integer unit of XRP; 1 XRP = 1,000,000 drops. XRP amounts are always integers of drops.
    Flag ledger A ledger (index divisible by 256) on which amendment/fee voting is tallied.
    IOU / issued currency A balance denominated in a non-XRP currency, represented as a RippleState (trust line) with mantissa/exponent precision.
    Keylet A typed, hashed key locating an object in the state tree (sha512Half of a type prefix + identifiers).
    LastLedgerSequence The last ledger index at which a transaction may apply; the expiry that makes reliable retry safe.
    Owner reserve Additional XRP locked (not spent) per owned ledger object (trust line, offer, etc.). Released when the object is deleted.
    Reserve Collective term for base + owner reserve: XRP held, not burned, to back ledger state.
    Sequence A per-account, monotonically increasing counter; a transaction is valid at exactly one sequence. Replay prevention.
    Standalone mode A private, peerless xrpld instance (-a) where you advance ledgers manually via ledger_accept. See Getting Started.
    server_definitions RPC method returning the full serialization codec (field metadata, transaction formats, ledger entry formats, flags, result codes) plus a SHA512Half hash of the entire payload. The hash is the canonical codec version identifier for custody and offline-signing systems — if the hash matches a cached copy, the codec is byte-identical and offline transaction construction is safe. See ch04 Custody.
    STAmount The value type holding either XRP drops (integer) or an IOU mantissa/exponent. See ch01 internals.
    Trust line A bilateral RippleState object encoding a credit limit and balance between two accounts for one currency.
    UNL / nUNL Unique Node List (the validators a node trusts) and the Negative UNL (validators temporarily excluded to preserve liveness). See ch01 consensus internals.
    Validated The only authoritative transaction state: included in a ledger agreed by consensus. Not the same as the preliminary engine result.
    xrpld The XRP Ledger server daemon (the software historically named rippled; the vendored source tree here retains the rippled/ directory name).

    • rippled/include/xrpl/protocol/TER.h — result-code enums, ranges, and the isTes*/isTec*/isTer*/isTef*/isTem*/isTel* predicates.
    • rippled/include/xrpl/protocol/TxFlags.h — tf* transaction flags and asf* AccountSet flags.
    • rippled/include/xrpl/protocol/LedgerFormats.h — lsf* ledger state flags.
    • rippled/include/xrpl/protocol/detail/sfields.macro — sf* serialized fields.
    • rippled/include/xrpl/protocol/detail/ledger_entries.macro — lt* ledger entry types.
    • rippled/include/xrpl/protocol/detail/transactions.macro — tt* transaction types.
    • rippled/src/xrpld/rpc/handlers/server_info/ServerDefinitions.cpp — handler that assembles and hashes the server_definitions response; hash is SHA512Half(canonical_json_of_all_definitions), computed once at startup.
