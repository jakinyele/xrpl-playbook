    Indexing (History & State)

    Why does this matter?

    The first non-trivial thing a migrant builds is usually a dashboard or a reconciliation job: "show me every transaction this account has ever made" or "show me every current holder of this token."

    On EVM the reflex is TheGraph, Etherscan, or a block-range eth_getLogs scan. None of those map directly. The XRPL distinguishes between History (what happened) and State (what is true now), and provides different tools for each:

    1. History is a per-account, cursor-paginated query (account_tx).
    2. State is a global ledger snapshot you can scan by type (ledger_data).
    3. Analytics should run against Clio, a purpose-built read replica.

    Mental model

    Two framings replace the EVM ones:

    1. There is no global event log to scan. EVM events are a global stream. XRPL history is the transactions that affected a given account, retrieved via account_tx. To index "all payments for my token," you must index the issuer's account history.
    2. The ledger is a KV store you can walk. If you need a snapshot (e.g., "current balances of all 10,000 holders"), you don't replay history. You walk the ledger_data stream for ltRIPPLE_STATE objects.

    Architecture

    The EVM habit → XRPL equivalent

    You know (EVM / Solana) XRPL equivalent Watch out
    TheGraph subgraph (History). Clio + account_tx. No mapping to deploy; query the JSON-RPC/WS API. No custom schema. You post-process account_tx results yourself.
    TheGraph subgraph (State). ledger_data — walk the entire ledger state by object type. Iterating 100M+ objects is slow; use for snapshots or specialized indexing.
    Etherscan API — txlist by address. account_tx — transactions by account, paginated by a marker. Range is by ledger index, not block number; cursor is a {ledger, seq} object.
    eth_getLogs over a range. No global log scan. Iterate account_tx per account, or subscribe live. Design around per-account history.

    account_tx vs. ledger_data — Mental model comparison

    Feature account_tx (History) ledger_data (State)
    Query unit Single account Global ledger snapshot
    Pagination marker: {ledger, seq} marker: <hex_key>
    Order forward: true/false (chronological) Hexadecimal key order
    Scope All txs affecting the account All objects in the ledger
    Use case Reconciliation, dashboards Holder lists, state snapshots

    State indexing: "Who holds my token?"

    To get a snapshot of all holders of an issued currency: 1. Call ledger_data with type: "state" (or ripple_state). 2. Filter results where the issuer/currency match your token. 3. Paginate using the returned marker until exhausted. 4. Optimization: hosted indexers (like Bithomp or XRPScan) maintain their own SQL/NoSQL indexes of these relations so you don't have to scan the whole ledger state for a single token's holders.

    account_tx vs. ledger_data — Parameter reference

    Parameter account_tx (History) ledger_data (State) Watch out
    ledger_index_min / max Inclusive range to search. N/A (single ledger) Use -1 for widest range on account_tx.
    ledger_index / hash Single ledger (API v2). The ledger to snapshot. Mutually exclusive with min/max.
    forward true/false (chronological). N/A (hex order) Keep constant across pagination.
    limit Min 10, max 400. Max 256 (JSON) or 2048 (binary). Page sizes are server-enforced; you must paginate.
    marker Object {ledger, seq}. String (hex key). Treat as opaque; pass back verbatim.

    Pagination loop: issue the first call with your range + limit; if the response contains a marker, call again with that same marker (and identical range/order/filters) until no marker is returned. Changing the range or forward direction between calls invalidates the cursor's meaning.

    Example flow

    "Reconcile every payment an account received last month" — the migrant job.

    On EVM you would scan a block range for Transfer logs to the address. On the XRPL:

    1. Point at Clio, not a validator. Choose a Clio endpoint (self-hosted or a provider) so deep history is actually retained and the query load is served by the read replica.
    2. Bound the range. Set ledger_index_min/ledger_index_max to the ledger indices spanning the month (or -1/-1 for everything available), fix forward to one direction, and set limit (≤ 400).
    3. Paginate to exhaustion. Loop account_tx, passing back each returned marker unchanged, until no marker comes back.
    4. Filter client-side. For each transaction, inspect the meta for delivered_amount and the transaction type — the ledger does not pre-filter "received payments" for you the way an event topic would.
    5. Cross-check finality. Every returned transaction is already validated; there is no reorg to reconcile against later.

    The lesson: history is a cursor walk per account against a read replica, and the semantic filtering you expressed as an event topic on EVM now happens in your own code over the returned metadata.

    Security considerations

    • Do not run analytical history load against a validator. It competes with consensus work and the node may not even retain the ledgers you need. Use Clio (or a provider) for history and indexing.
    • Treat the marker as opaque. Never parse, mutate, or persist it as a reconstructable offset; store and replay it verbatim. Synthesizing markers is a source of silent gaps.
    • Verify the data window. A "complete" answer depends on the server's retained ledger range; confirm the endpoint actually covers the range you are querying (server_info → complete_ledgers) before trusting a result set.
    • Do not assume a provider's non-standard indexes exist everywhere. Hosted indexers may add convenience endpoints beyond account_tx; code to the standard API so you can fail over.

    Common mistakes

    • Expecting a global log scan. There is no eth_getLogs equivalent; iterate per account or subscribe live.
    • Using limit as if it were unbounded. Values above 400 are capped; you still must paginate.
    • Flipping forward or changing the range mid-pagination. This invalidates the cursor and produces gaps or duplicates.
    • Querying a validator for deep history. It may have deleted old ledgers via online deletion; point historical reads at Clio.
    • Confusing ledger index with block number. Ranges are ledger indices; there is no "block."

    Production checklist

    • [ ] Historical/analytical reads target Clio (or a provider running one), not a validating node.
    • [ ] account_tx pagination passes the returned marker back verbatim and loops until no marker remains.
    • [ ] Range (ledger_index_min/max), forward, and filters are held constant across a pagination run.
    • [ ] limit respects the 10/200/400 min/default/max envelope.
    • [ ] The queried endpoint's complete_ledgers window is verified to cover the requested range.
    • [ ] Semantic filtering (payment vs. other types, delivered_amount) is done client-side over meta.

    What I learned

    • History is account-shaped, not log-shaped. The single most important reframing: you cannot filter the whole chain by a topic; you walk each account's transactions. Dashboards are built by choosing which accounts to index, not which events to subscribe to globally.
    • Clio is the archive/subgraph analogue, and it is a first-class concept. Sending history load to a validator is the equivalent of pointing your indexer at a consensus-critical node — technically possible, operationally wrong.
    • The marker is the whole pagination contract. Because it is an opaque {ledger, seq} cursor rather than an offset, correct pagination is entirely about replaying it faithfully and holding every other parameter constant.

    Open questions

    Does Clio serve the exact same command set as xrpld, or a subset/superset?

    Confirmed against source (API surface): the public command vocabulary is the rippled/ dispatch table in src/xrpld/rpc/detail/Handler.cpp; Clio is designed to answer the same public API for reads. Educated guess (not verified in this vendored tree, which does not include Clio): Clio focuses on read/history methods and delegates or omits some admin/submission commands, and may retain deeper history than a default node. Confirm the specific method coverage and retention window against the Clio server you actually target before depending on it.

    What is the cheapest way to get a full historical sync of one account?

    Educated guess (operational, not protocol-encoded): use account_tx with binary: true and limit: 400, paginating by marker, against a Clio endpoint with a complete_ledgers window covering the account's whole life; decode client-side. The trade-off between binary bulk sync and JSON convenience is an application decision, not a protocol rule.
