    Subscriptions & the Event Model

    Why does this matter?

    On EVM your "push" toolkit is indexed event logs, eth_subscribe("logs"), and webhooks keyed by contract + topic. On the XRPL there are no events and no contract topics. Instead a single WebSocket subscribe command opens named streams and per-account feeds that push structured messages as the ledger advances. If you carry over the logs/topics mental model unchanged, you will look for a filter abstraction that does not exist and miss the one that does.

    This section maps that mental model and pins every stream name and message type to the rippled/ source that emits it, so you know the exact strings on the wire.

    Mental model

    Three reframings:

    1. You subscribe to streams and accounts, not to event signatures. The subscribe command takes a streams array (network-wide feeds) and/or accounts array (per-account transaction feeds) and/or books (order-book feeds). There is no per-contract, per-topic filter because there are no contracts or topics.
    2. The transaction feed is the event log. Every effect on the ledger is a transaction with structured meta. Watching an account's transactions (with delivered_amount, affected nodes, engine_result) is the XRPL equivalent of consuming that account's event log — you filter client-side on the transaction type and metadata.
    3. Same command, both transports, same vocabulary. subscribe is the same dispatcher command as the reads in RPC Method Mapping, just held open over WebSocket. There is no separate pub/sub protocol.

    Architecture

    The EVM habit → XRPL equivalent

    You know (EVM) XRPL equivalent Watch out
    eth_subscribe("newHeads") subscribe streams: ["ledger"] → ledgerClosed messages. Fires once per validated ledger (~3–5s), carrying ledger_index, ledger_hash, fee_base, reserve_base/reserve_inc, txn_count. Use it to drive fee/reserve refresh, not a block counter.
    eth_subscribe("logs", {address, topics}) subscribe accounts: [...] → transaction messages for those accounts. No topic filter. You get every transaction touching the account; filter client-side by TransactionType and meta.
    Global log firehose subscribe streams: ["transactions"] → every validated transaction. This is the whole network's validated transaction stream — high volume. Prefer accounts unless you truly need everything.
    newPendingTransactions (mempool) streams: ["transactions_proposed"]; per-account accounts_proposed. These are proposed (not yet validated) — the closest thing to a mempool feed. Never treat a proposed transaction as final.
    Order-book / price websocket (off-chain) subscribe books: [{taker_pays, taker_gets, ...}]. Native order-book feed. Options include snapshot (initial state) and both (both sides of the book).
    Webhook keyed by event (No native webhooks.) Run a subscriber that consumes the stream and fans out. You own the delivery/retry layer; the ledger pushes over the open socket, it does not POST to your URL.

    Stream names and the message type they emit

    Each general stream is requested by its exact string in the streams array; the pushed messages carry a type field set by the publisher:

    streams value Emits type Use it for
    "ledger" ledgerClosed Per-ledger tick: fee/reserve refresh, ledger index/hash, txn_count.
    "transactions" transaction Every validated transaction network-wide.
    "transactions_proposed" transaction (with validated: false) Proposed (pre-consensus) transactions.
    "validations" validationReceived Validator validation messages (advanced/monitoring).
    "manifests" manifestReceived Validator manifest updates.
    "server" serverStatus Local server state changes (e.g. sync status, load).
    "consensus" consensusPhase Consensus phase transitions (advanced).
    "peer_status" peerStatusChange Admin-only peer status.
    "book_changes" (book-changes message) Aggregated order-book changes per ledger.

    Per-account feeds use the accounts (validated) and accounts_proposed (proposed) arrays; both deliver transaction messages filtered to those accounts. Order-book feeds use books.

    The transaction message — what you actually consume

    The transaction message (the workhorse) carries:

    • type: "transaction".
    • validated: true once in a validated ledger (the finality signal).
    • engine_result: the result code (tesSUCCESS, a tec…, etc.).
    • transaction: the transaction JSON itself.
    • meta: the metadata, including affected nodes and (for payments) delivered_amount injected by the server.
    • ledger_index: the ledger it was included in.

    Example flow

    "Notify my service the moment an account receives a payment" — the webhook reflex.

    On EVM you would register a webhook or eth_subscribe("logs") on the token contract filtered to the address. On the XRPL:

    1. Open a WebSocket to a public (or your own) server.
    2. Subscribe to the account: send subscribe with accounts: ["rYourAccount…"].
    3. Consume transaction messages as they arrive; each carries engine_result, meta, and validated.
    4. Filter client-side: keep the ones where TransactionType is Payment, the account is the Destination, and meta.delivered_amount is what you expected.
    5. Act only on validated: true. A message can arrive for a proposed transaction (if you subscribed to accounts_proposed); treat only validated ones as final.
    6. Own the delivery layer. The ledger pushes over the socket; your service is responsible for reconnect, resubscribe, and gap-recovery via account_tx after a disconnect.

    The lesson: the transaction stream is the event log, the finality signal is validated, and there is no server-side topic filter — you subscribe by account and filter on metadata yourself.

    Security considerations

    • Never treat proposed transactions as final. transactions_proposed / accounts_proposed are pre-consensus; acting on them is the equivalent of crediting an unconfirmed mempool transaction. Gate all value logic on validated: true.
    • Assume the socket will drop. On reconnect you must resubscribe and backfill the gap with account_tx, or you will silently miss transactions that closed while you were disconnected. The stream has no built-in replay.
    • Do not subscribe to transactions (firehose) when accounts will do. The network-wide stream is high volume and easy to fall behind on; scope to the accounts you care about.
    • Admin-only streams stay private. peer_status (and other admin feeds) are role-gated; never expose them on a public endpoint.

    Common mistakes

    • Looking for a topic/event filter. There is none; subscribe by account and filter on TransactionType/meta client-side.
    • Acting on proposed messages. Confusing accounts_proposed with accounts, and crediting pre-consensus transactions.
    • No gap-recovery after reconnect. Assuming the stream resumes where it left off; it does not — backfill with account_tx.
    • Polling tx in a loop when a subscription is cheaper. For live confirmation the transactions/accounts stream beats hammering tx.
    • Expecting the ledger to POST a webhook. Delivery is over the open socket; you build the fan-out.

    Production checklist

    • [ ] Value/finality logic keys off validated: true, never a proposed message.
    • [ ] The subscriber resubscribes and backfills via account_tx after any disconnect (no assumed replay).
    • [ ] Subscriptions are scoped (accounts/books) rather than the full transactions firehose unless genuinely required.
    • [ ] Each consumed transaction is filtered by TransactionType and validated meta (e.g. delivered_amount) before acting.
    • [ ] Admin-only streams (peer_status, etc.) are not reachable publicly.
    • [ ] The ledger stream drives fee/reserve refresh rather than a block counter carried over from EVM.

    What I learned

    • The transaction stream is the event log — there is nothing else to find. Once you accept that effects are transactions with meta, the missing "events" abstraction stops feeling like a gap and starts feeling like a simplification: one feed, filtered client-side.
    • Finality is a field, not a confirmation count. validated: true is the entire "is it final?" question, delivered inline on the message — which is why proposed streams exist as a clearly separate, clearly unsafe channel.
    • The client owns durability. No replay, no webhooks: the correct production pattern is subscription for liveness plus account_tx for gap-recovery, which ties this section directly to Indexing & Historical Queries.

    Open questions

    After a disconnect, is there any server-side replay, or must I always backfill with account_tx?

    Confirmed against source (mechanism): subscribe registers a live feed in Subscribe.cpp; messages are pushed as ledgers close via the publish paths in NetworkOPs.cpp. There is no replay buffer in that path. Educated guess (operational): the robust pattern is to record the last processed ledger_index from the ledger/transaction stream and, on reconnect, backfill the gap with account_tx before trusting the live feed again. Verify the exact reconnection guarantees of any hosted provider you use.

    Does subscribing to accounts guarantee I see every transaction that affects the account, including ones where it is not the sender?

    Educated guess (not fully verified in this vendored tree): the accounts feed is documented as delivering transactions that affect the subscribed accounts (as sender or as an affected party in meta), not only those it signs. Confirm against the Subscribe.cpp account-feed matching logic and the network you target before relying on it for inbound-only accounting.
