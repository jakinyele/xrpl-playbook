    RPC Method Mapping

    Why does this matter?

    On day one of a port, you are not thinking about consensus philosophy — you are thinking "which call replaces eth_getBalance?" This section is that lookup. It maps the JSON-RPC / SDK calls you reach for reflexively on EVM (and, where it differs, Solana) to their XRPL equivalents, with a Watch out on every call whose shape or semantics differ enough to bite you.

    Every XRPL method here is a real command string registered in the rippled/ dispatch table (src/xrpld/rpc/detail/Handler.cpp), so the spelling is canonical — you can send it over both JSON-RPC (HTTP POST) and WebSocket.

    Mental model

    Three framing differences drive every row below:

    1. One endpoint, method + params, not a fixed method namespace. EVM exposes a closed eth_* / net_* namespace. The XRPL exposes a single command dispatcher: you send {"method": "account_info", "params": [...]}. The same command works over HTTP and WebSocket.
    2. Read the ledger directly, not "call a view function." There is no eth_call because there is no contract to call. State reads are typed queries against ledger objects (account_info, account_lines, ledger_entry) — you ask for the object, not for the result of running code.
    3. account (r-address), not from/to topics. Almost every read is keyed by an XRPL account address, and history/subscription filters are by account, not by contract address or event signature.

    Architecture

    Reads — balances & account state

    You call (EVM / Solana) XRPL equivalent Watch out
    eth_getBalance / getBalance (SOL) account_info — returns the AccountRoot (XRP balance in drops, Sequence, flags, OwnerCount). Returns XRP only. IOU balances live in trust lines, not the account — you need account_lines. Balance is in drops (1 XRP = 1,000,000 drops).
    ERC-20 balanceOf (an eth_call) account_lines — lists trust lines (per-issuer, per-currency IOU balances). There is no per-token contract to call. One call returns all the holder's IOU balances as signed amounts relative to each issuer. Paginated via marker.
    Reading a token's total supply / config gateway_balances (issuer's obligations) / account_objects (owned ledger objects). "Total supply" is the sum of the issuer's outstanding obligations, not a contract field.
    eth_getTransactionCount (nonce) account_info → account_data.Sequence. The account Sequence is the nonce equivalent; there is no separate call.

    Reads — contract calls & simulation

    You call XRPL equivalent Watch out
    eth_call (view function) ledger_entry — fetch a specific ledger object by key/type (offer, escrow, AMM, trust line, MPT issuance…). No code executes. You are reading typed state directly. Pick the object type you actually want rather than calling a getter.
    eth_call for a quote / route ripple_path_find (interactive) or path_find (WebSocket subscription that streams updated paths). Pathfinding is the XRPL's "quote": it finds routes across order books + AMM for a cross-currency payment. ripple_path_find is one-shot; path_find streams.
    eth_estimateGas fee — current base fee, load factor, and queue state; plus server_info. Cost is not "gas for this call." It is a network-load fee (see ch01 payments). You do not estimate per-operation compute.
    Reading a DEX order book (contract call / subgraph) book_offers — the live order book for a (taker_pays, taker_gets) pair. The book is a native ledger structure keyed by the currency/issuer pair; it always exists without anyone "deploying" it.

    Writes — submitting transactions

    You call XRPL equivalent Watch out
    eth_sendRawTransaction (pre-signed) submit with a signed tx_blob. You sign client-side (SDK) and submit the blob. This is the production path.
    Sign-then-send in one call (dev convenience) submit with tx_json + secret (admin/local only). Never send a seed to a remote server. Use client-side signing + tx_blob in production.
    Multisig submission submit_multisigned — a tx_json carrying a Signers array. Collect signatures out-of-band (sign_for), then submit the assembled multisigned transaction. See ch04 security.
    eth_getTransactionReceipt tx — look up a transaction by hash; check validated: true and the meta result. A missing/validated:false result is not failure — it may simply not be in a validated ledger yet. Poll until validated or LastLedgerSequence passes (see ch01 getting-started).

    Reads — history (see the dedicated section)

    You call XRPL equivalent Watch out
    eth_getLogs / block-range scans / subgraph account_tx — paginated transaction history for one account. Keyed by account, not by contract/event topic. Pagination and range semantics are non-obvious — see Indexing & Historical Queries.

    Example flow

    "Check a balance, quote a swap, submit it, confirm it" — the EVM reflex vs the XRPL calls.

    On EVM you might: eth_getBalance → eth_call a router's getAmountsOut → eth_estimateGas → eth_sendRawTransaction → poll eth_getTransactionReceipt. On the XRPL the same job is:

    1. Balance: account_info for XRP, or account_lines for the IOU you hold.
    2. Quote: ripple_path_find with your source_currencies and the destination amount — it returns concrete paths across the DEX and AMM.
    3. Fee: fee (or read server_info) for the current base fee and load factor; autofill it into the transaction rather than estimating per-op gas.
    4. Submit: sign client-side, then submit the tx_blob.
    5. Confirm: tx by hash, waiting for validated: true — or watch the transactions subscription instead of polling.

    The lesson: the read side is direct typed queries, and the "quote" is pathfinding — there is no view function to call because there is no code to run.

    Security considerations

    • Never send a secret/seed to a remote server. The submit-with-secret and sign conveniences are for local/admin nodes only. Production signs client-side and submits a tx_blob. See ch04 security.
    • Do not treat a missing tx result as failure. Absence means "not in a validated ledger yet," not "rejected." Key retry/finality logic off validated + LastLedgerSequence, not off a 404-style absence.
    • Admin-only methods are a footgun on public endpoints. Commands like sign, wallet_propose, ledger_accept, and stop are gated by role; never expose an admin-configured port publicly.
    • Read amounts in the right units. account_info returns XRP in drops; IOU amounts are objects ({currency, issuer, value}), not integers. Mixing the two is a classic port bug.

    Common mistakes

    • Calling account_info and expecting IOU balances. It returns XRP only; reach for account_lines.
    • Looking for eth_call. There is no contract to call — use ledger_entry for state and ripple_path_find for quotes.
    • Estimating "gas" per operation. The fee is network-load-based, not per-opcode; use fee/server_info.
    • Scanning "blocks" for events. History is per-account via account_tx, not a global log scan; event streams come from subscribe.
    • Submitting tx_json + secret to a public server. Sign locally; submit a tx_blob.

    Production checklist

    • [ ] All state reads mapped to concrete commands (account_info, account_lines, account_objects, ledger_entry, book_offers).
    • [ ] Quotes/routes use ripple_path_find/path_find, not a "view call."
    • [ ] Signing is client-side; only tx_blob (or submit_multisigned) is sent to the server.
    • [ ] Confirmation logic uses tx + validated + LastLedgerSequence, not receipt-absence.
    • [ ] Fee handling reads fee/server_info; no per-operation gas estimation carried over.
    • [ ] No admin-only method (sign, wallet_propose, ledger_accept, stop) is reachable on a public endpoint.

    What I learned

    • The read side is the biggest reflex to unlearn. There is no eth_call because there is no code path to invoke — every read is a typed query against a named ledger object. Once that clicks, the whole read namespace maps cleanly.
    • "Quote" is pathfinding, not a view function. ripple_path_find is the closest thing to getAmountsOut, and it is a first-class protocol capability, not a helper contract someone deployed.
    • One dispatcher, two transports. The same method string works over HTTP and WebSocket, which is why the subscription model (next section) reuses the exact command vocabulary rather than introducing a parallel one.

    Open questions

    Is there a single call that returns everything about an account (XRP + all IOUs + all owned objects) in one round trip?

    Confirmed against source (per-command): the reads are split by object type — account_info (the AccountRoot), account_lines (trust lines), account_objects (owned objects), each a distinct handler in src/xrpld/rpc/handlers/account/. Educated guess (composition): a full account snapshot is assembled client-side by combining these calls (each paginated by marker); there is no single "get account state" super-command in the base handler set. Verify the exact object coverage you need against account_objects before assuming one call suffices.

    When should a migrant use path_find (streaming) instead of ripple_path_find (one-shot)?

    Educated guess (operational, not protocol-encoded): ripple_path_find returns paths once, suited to a request/response quote; path_find is a WebSocket subscription that keeps re-computing paths as the ledger changes, suited to a live trading UI. The trade-off (freshness vs. connection cost) is an application decision, not a protocol rule.
