    Chapter 6 — Features and Amendments

    Every capability on the XRP Ledger — from payment channels to NFTs, AMM pools to confidential transfers — arrives as an amendment. Understanding the amendment pipeline tells you what the network can do today, what is coming next, and what operational risk each change poses to your system.

    Read this chapter after Chapter 4 (Hardening → Operations). The amendment lifecycle mechanics are covered there; this chapter focuses on the features themselves.

    Architect's Intent

    "The amendment system was designed to allow the network to evolve without disruptive hard forks. The validators themselves — not any single company — decide when a change goes live. That's the whole point." — David Schwartz (JoelKatz), paraphrased from the original amendment RFC

    When Schwartz, McCaleb, and Britto shipped rippled 0.31.0 in 2016, they faced a problem every decentralized network eventually hits: how do you change the rules without breaking the network or trusting a central authority to call the shot?

    Bitcoin's answer at the time was a contentious hard fork. The XRPL's answer was to make protocol evolution a first-class, on-ledger process:

    • Validators vote by embedding amendment preferences in the validations they already sign every ledger — no separate election, no out-of-band coordination.
    • A supermajority (≥ 80%) must hold for two consecutive weeks before anything activates — a deliberate social buffer that gives every operator time to upgrade.
    • Activation is irreversible — the ledger's own append-only history enforces it. A flawed amendment is not "turned off"; it is superseded by a corrected successor (exactly what happened with Batch → BatchV1_1 and PermissionDelegation → PermissionDelegationV1_1).
    • A node that cannot process an enabled amendment fails loud (visible as amendment_blocked in server_info) rather than silently forking.

    The design philosophy is the same one that runs through the whole ledger: make illegal states unrepresentable or immediately detectable. A stale node fails safe. An unactivated feature returns temDISABLED before it can claim a fee. A flawed amendment is retired, not deleted. Every mechanism favors a loud halt over a silent inconsistency.

    This chapter is the operational expression of that philosophy: know exactly what the network supports, what it is about to support, and what to do when the answer changes.

    Why this chapter comes before Chapter 5

    Reference architectures (ch05) must be grounded in what the network actually supports today vs. what is coming. Building an architecture on an unactivated amendment is a design risk. This chapter provides the status reference that ch05 depends on.

    Sections

    Section Scope
    Feature Reference Version compatibility matrix (xrpld 1.10–3.3); active, voting, and in-development features grouped by domain; use-case guide for each feature group; obsolete amendment notes.

    Reading order

    1. Start here — read the chapter overview for the amendment lifecycle mental model (why features are permanent once activated, what Supported::No means, what VoteBehavior::DefaultNo implies for your validator).
    2. Feature Reference — use as a reference when building or planning: check whether the feature you need is active, voting, or still in development, and which minimum xrpld version to target.
    3. Cross-reference Operations — for the amendment monitoring runbook: how to detect upcoming activations and upgrade your node before becoming amendment-blocked.

    ⚠️ Devnet ≠ Mainnet. Devnet runs with many amendments force-enabled via feature force_enable in the rippled.cfg. Code that works on Devnet may silently rely on amendments that are still voting (or not yet votable) on Mainnet. Always verify feature status against server_info on the target network before shipping. A feature active on Devnet that returns temDISABLED on Mainnet will cause silent, hard-to-debug submission failures in production.

    What you should be able to do after this chapter

    • State the current mainnet status of any feature covered in this chapter (active, voting, in-development, or obsolete).
    • Identify the minimum xrpld version required to use a given feature in your application.
    • Explain why Batch and PermissionDelegation are listed as obsolete and which amendments replaced them.
    • Select the correct amendment set to enable on a private test network for a specific use case.
    • Build an upgrade and activation monitoring plan for features currently open for voting that your application depends on.
