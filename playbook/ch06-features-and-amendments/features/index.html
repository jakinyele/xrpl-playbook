    Feature Reference

    Why does this matter?

    XRPL features are permanent once activated — no rollback, no opt-out. A transaction type or ledger entry type introduced by an unactivated amendment returns temDISABLED. An architecture built on an amendment that later stalls in voting will not ship on schedule. This reference gives you the current activation status, minimum xrpld version, and the practical use cases for every significant feature through xrpld 3.3.

    Mental model

    The amendment lifecycle has four stages, derived from the source:

    stateDiagram-v2
    [*] --> InDevelopment : merged into xrpld\n(Supported::No)

    InDevelopment --> OpenForVoting : Supported::Yes\n(API frozen; validators can vote)

    OpenForVoting --> MajorityHeld : ≥ 80% of UNL\nvotes yes on a flag ledger\n(DefaultNo: opt-in)\n(DefaultYes: auto-voted)

    MajorityHeld --> Active : majority held\ncontinuously for 2 weeks →\nEnableAmendment pseudo-tx\nat next flag ledger

    MajorityHeld --> OpenForVoting : majority lost\nbefore 2 weeks\n(clock resets)

    Active --> Retired : ≥ 2 years active →\ngating code removed\nfrom xrpld source\n(still fully live on Mainnet)

    OpenForVoting --> Obsolete : superseded by a\ncorrected amendment\n(e.g. Batch → BatchV1_1)

    note right of InDevelopment
        temDISABLED on all networks.
        Only on private devchains
        with force_enable.
    end note

    note right of Active
        Permanent. Irreversible.
        Cannot be turned off.
    end note

    note right of Retired
        "Retired" ≠ deactivated.
        Still enforced on Mainnet;
        the gating toggle was deleted.
    end note

    "Retired" does not mean deactivated — it means the opposite. A retired amendment is still permanently enabled on Mainnet. It has simply been active long enough (≥ 2 years) that it is now a mandatory part of the protocol, so xrpld deleted the old "if this amendment is enabled" toggle code and moved the identifier to its deprecated XRPL_RETIRE_FEATURE list in features.macro. A retired amendment can never be turned off. Retirement is a source-code cleanup milestone, not a deactivation. This is why the tables below show entries like Escrow as ✅ Active (retired): fully live on Mainnet, and so entrenched that its gating code no longer exists.

    Obsolete = supported but permanently flagged as never-to-be-voted-for. This happens when an amendment is replaced by a corrected version.

    History of amendments

    The problem amendments were built to solve

    Every blockchain eventually needs to change its rules. The conventional answer is a hard fork: operators coordinate off-chain to run new software by a flag date, and nodes that miss the date end up on a diverging chain. For a decentralized value-settlement network that is a serious hazard — a botched or contested fork can split the ledger, and "the rules changed out from under me" is exactly the failure a settlement system cannot tolerate.

    The XRP Ledger's answer, introduced in rippled 0.31.0 (2016), was to make protocol evolution a first-class, on-ledger process rather than an off-chain social coordination problem. The design goal, in the original framing, was "sensible evolution": let the network adopt new features without disruptive hard forks, with the validators themselves — not any single company — deciding when a change goes live, and with an explicit safety mechanism for nodes that fall behind. This is why the amendment system predates most of the features this chapter documents: it is the substrate that made all of them shippable.

    From idea to on-ledger switch

    The insight that makes the system work is that a rule change does not need a new chain — it only needs a coordinated flag day that the ledger itself records and enforces. The mechanism has three moving parts, all visible in xrpld source:

    1. The vote rides on validations. Each validator publishes its amendment preferences in the sfAmendments field of the validations it already signs every ledger (src/xrpld/app/misc/detail/AmendmentTable.cpp — see doVoting()). No separate election is needed; governance piggybacks on consensus.
    2. The network writes its own transactions. When an amendment's support crosses the threshold, the network injects an EnableAmendment pseudo-transaction — transaction type ttAMENDMENT (100), include/xrpl/protocol/detail/transactions.macro — that no account submits. It is applied by the Change transactor (src/libxrpl/tx/transactors/system/Change.cpp, applyAmendment()).
    3. The ledger holds the canonical state. applyAmendment() maintains the Amendments singleton object (keylet::amendments()): a running sfMajorities array (each entry an amendment plus the sfCloseTime when it first reached majority — the start of the clock) and the sfAmendments list of what is permanently enabled. The tfGotMajority flag adds an entry and starts the timer; tfLostMajority removes it and resets the timer; an EnableAmendment with no flag pushes the amendment into sfAmendments and enables it for good.

    The activation rule sits on top of that state: an amendment enables only after it has held ≥ 80% support for two consecutive weeks (kAmendmentMajorityCalcThreshold = 80/100 and kDefaultAmendmentMajorityTime = weeks{2} in include/xrpl/protocol/SystemParameters.h; the gate (*majorityTime + majorityTime_) <= closeTime in AmendmentTable.cpp). Because losing majority resets the sfCloseTime, the two-week clock is a sustained threshold, not a one-time poll — a design choice that favors stability over speed. See ch04 Operations for the operator-facing side of these same constants.

    The safety valve: amendment-blocking

    The other half of "no disruptive hard forks" is what happens to a node that is behind. When applyAmendment() enables an amendment the local build does not understand, it calls setAmendmentBlocked() (Change.cpp) and the node stops processing rather than applying rules it cannot validate correctly. A stale node fails safe and loud (visible as server_info.amendment_blocked) instead of silently diverging onto its own fork. This is the mechanism that lets the network upgrade itself without splitting.

    Milestones and lessons

    • FeeEscalation — the first activated amendment (2016-05-05). Fittingly, the amendment system's debut change hardened the network under load (transaction-cost escalation), proving the pipeline on an operational fix before feature work.
    • MultiSign — governance enabling security. Multi-signing shipped as one of the earliest amendments, establishing the pattern that even account-security primitives arrive through the same vote.
    • Feature waves. Escrow and payment channels, then Flow (the rewritten payment engine), later the AMM, and most recently permissioned tokens and DEX — each entered through the identical pipeline, which is why this chapter can describe them uniformly as active / voting / in-development.
    • Obsoletion is part of the design, not a failure of it. Batch and PermissionDelegation were superseded by corrected versions (BatchV1_1, PermissionDelegationV1_1); the originals are marked permanently un-votable rather than deleted. The lesson: because activation is irreversible, a flawed amendment is retired by shipping a fixed successor, not by "turning it off" — reinforcing why the two-week sustained threshold and validator opt-in exist in the first place.

    Architecture

    How amendments affect your code

    • New transaction type — submitting before activation → temDISABLED.
    • New ledger entry type — ledger_entry queries return nothing or errors.
    • New RPC method — returns unknown command on nodes below the minimum version.
    • Flag changes — new flags on existing transactions are silently ignored or error depending on whether the amendment is active.

    Always check server_info.amendment_blocked on any production node. A value of true means the node is running software that does not support an enabled amendment — it is no longer tracking the live ledger.

    Version compatibility matrix

    Status key: ✅ Active — enabled on Mainnet | 🗳️ Voting — open, not yet activated 🔧 Dev — Supported::No; not votable | ⚠️ Obsolete — removed/replaced

    ✅ Active (retired) — enabled on Mainnet and active for 2+ years, so its amendment-gating code has been removed from xrpld (identifier moved to the XRPL_RETIRE_FEATURE list). It is still fully active and can never be disabled — "retired" refers only to the source-code cleanup, not to the amendment's status on the ledger. Do not read (retired) as "off" or "deprecated feature."

    Sources: features.macro (xrpld 3.3 branch), xrpscan.com/amendments (live Mainnet status), xrpl.org/resources/known-amendments, API-CHANGELOG.md.

    Fungible Tokens and Issuance

    Feature Introduced Mainnet Status Activated
    Clawback v1.12.0 ✅ Active (retired) 2024-02-08
    MPTokensV1 v2.3.0 ✅ Active 2025-10-01
    AMMClawback v2.3.0 ✅ Active 2025-01-30

    MPTokensV1 use case (XLS-33): Introduces Multi-Purpose Tokens (MPTs) — a simpler, more gas-efficient alternative to Trust Line tokens. MPTs live in MPTokenIssuance (issuer settings) and MPToken (holder balance) objects. No bidirectional trust line required. Supports transfer fees, clawback, and locking. Payments can deliver MPTs natively. Optimal for stablecoins and high-volume fungible token use cases where trust-line overhead is undesirable.

    DynamicMPT — Source-verified deep dive:

    DynamicMPT adds a two-phase capability model to MPTs: capabilities you intend to enable post-creation must be declared at issuance creation time via a new sfMutableFlags field. Without the corresponding lsmfMPTCanEnable* bit, the post-creation mutation is permanently blocked.

    Phase 1 — at MPTokenIssuanceCreate (sfMutableFlags declares future capabilities):

    Creation sfMutableFlags bit Meaning
    tmfMPTCanEnableCanLock Allows enabling holder-locking later
    tmfMPTCanEnableRequireAuth Allows enabling RequireAuth later
    tmfMPTCanEnableCanEscrow Allows escrowing tokens later
    tmfMPTCanEnableCanTrade Allows enabling DEX trading later (lsfMPTCanTrade)
    tmfMPTCanEnableCanTransfer Allows enabling peer-to-peer transfer later
    tmfMPTCanEnableCanClawback Allows enabling issuer clawback later
    tmfMPTCanMutateMetadata Allows updating MPTokenMetadata after creation
    tmfMPTCanMutateTransferFee Allows updating TransferFee after creation
    tmfMPTCannotEnableCanHoldConfidentialBalance Permanently blocks enabling confidential mode (opt-out lock)

    Phase 2 — at MPTokenIssuanceSet (sfMutableFlags enables a declared capability):

    Set sfMutableFlags bit Effect on issuance
    tmfMPTSetCanLock Sets lsfMPTCanLock
    tmfMPTSetRequireAuth Sets lsfMPTRequireAuth
    tmfMPTSetCanEscrow Sets lsfMPTCanEscrow
    tmfMPTSetCanTrade Sets lsfMPTCanTrade (prerequisite for MPTokensV2 DEX)
    tmfMPTSetCanTransfer Sets lsfMPTCanTransfer
    tmfMPTSetCanClawback Sets lsfMPTCanClawback
    tmfMPTSetCanHoldConfidentialBalance Enables encrypted balances (requires ConfidentialTransfer)

    Key source constraints (from MPTokenIssuanceCreate.cpp / MPTokenIssuanceSet.cpp):

    • Capabilities are one-way. Once enabled, lsfMPTCanLock, lsfMPTRequireAuth, etc. cannot be disabled. There is no unset path in the current implementation.
    • TransferFee update — fee can only be set non-zero if lsfMPTCanTransfer was already active before the mutation. Setting fee to 0 removes the field from the ledger entry.
    • Metadata update — setting to an empty blob removes the field. Maximum length: kMaxMpTokenMetadataLength.
    • Confidential mode is exclusive of transfer fees. TransferFee > 0 and lsfMPTCanHoldConfidentialBalance cannot coexist — amounts are encrypted so a percentage fee is not computable on-chain.
    • Encryption keys are set-once. sfIssuerEncryptionKey and sfAuditorEncryptionKey can be set via MPTokenIssuanceSet but cannot be updated after being set (tecNO_PERMISSION).
    • featureDynamicMPT gates all mutation. Without the amendment active, any MPTokenIssuanceSet that includes sfMutableFlags, sfMPTokenMetadata, or sfTransferFee returns temDISABLED.

    Practical use cases: - Regulatory compliance trigger — issue a token that allows clawback or RequireAuth to be enabled if a regulatory order requires it, without baking those constraints into every holder's initial experience. - Progressive feature rollout — ship a stablecoin with basic transfer, then enable DEX trading (tmfMPTSetCanTrade) once liquidity infrastructure is ready. - Metadata refresh — update MPTokenMetadata URI when hosted asset metadata moves (e.g., off-chain document location changes). - Fee tier changes — adjust TransferFee without reissuing (only if tmfMPTCanMutateTransferFee was declared at creation).

    MPTokensV2 — DEX integration for MPTs (in dev, XLS-82):

    MPTokensV2 (Supported::No in xrpld 3.3) extends the native DEX and AMM to treat MPTs as first-class tradeable assets alongside XRP and Trust Line tokens.

    What changes when MPTokensV2 activates:

    Transaction type New MPT behavior
    OfferCreate TakerGets / TakerPays may be MPT amounts (requires lsfMPTCanTrade on the issuance)
    Payment (cross-currency) Pathfinding can route through MPT-denominated order book hops
    AMMCreate Either pool asset can be an MPT
    AMMDeposit/Withdraw Standard LP token flow extended to MPT reserves
    Checks (CheckCreate/Cash) MPT amounts accepted

    The lsfMPTCanTrade issuance flag (set at creation via tfMPTCanTrade, or post-creation via DynamicMPT + tmfMPTSetCanTrade) is the DEX gate: an MPT issuance without lsfMPTCanTrade cannot appear in offers or AMM pools even after MPTokensV2 activates. This means issuers opt in to DEX trading explicitly, which matters for regulated stablecoins that should not appear in open order books.

    Source status: Supported::No in features.macro — not votable in any released xrpld version. Available on private Devnet chains only. Do not include in mainnet architecture plans until status changes to Supported::Yes.

    DynamicMPT + MPTokensV2 dependency matrix:

    Goal Requires
    Issue an MPT MPTokensV1
    Update MPT metadata or fee post-issuance MPTokensV1 + DynamicMPT
    Enable DEX/AMM trading for an MPT MPTokensV1 + MPTokensV2 + lsfMPTCanTrade on issuance
    Enable DEX trading on an MPT that was issued without lsfMPTCanTrade MPTokensV1 + DynamicMPT + MPTokensV2 (enable lsfMPTCanTrade post-creation, then trade)
    Enable confidential MPT balances MPTokensV1 + ConfidentialTransfer (+ DynamicMPT if enabling post-creation)

    DeFi, DEX, and Markets

    Feature Introduced Mainnet Status Activated
    AMM v1.12.0 ✅ Active 2024-03-22
    fixAMMv1_1 v2.2.0 ✅ Active 2024-09-24
    fixAMMv1_2 v2.3.0 ✅ Active 2025-01-30
    fixAMMv1_3 v2.5.0 ✅ Active 2025-08-29
    AMMClawback v2.3.0 ✅ Active 2025-01-30
    DeepFreeze v2.4.0 ✅ Active 2025-05-04
    PermissionedDEX v2.5.0 ✅ Active 2026-02-18

    AMM use case (XLS-30): Adds a geometric-mean automated market maker (AMMCreate, AMMDeposit, AMMWithdraw, AMMVote, AMMBid, AMMDelete). The pool invariant is LPTokenBalance ≤ sqrt(asset1 × asset2), which produces constant-product-like pricing for marginal swaps. Each AMM is a protocol-owned account holding two asset reserves. LP tokens are minted as Trust Line tokens against the AMM account. The continuous auction slot (AMMBid) lets one LP trade at a discount for a time window.

    AMMClawback use case: Allows issuers with clawback rights to claw back Trust Line tokens that are currently held inside an AMM pool. Required for regulatory compliance by issuers who hold lsfAllowTrustLineClawback.

    DeepFreeze use case (XLS-77): Adds a "deep freeze" state to trust lines — stronger than the existing individual freeze. A deeply-frozen trust line cannot receive or send the token, and cannot be used in payments or AMM deposits, even by the holder. Targets issuers who need to enforce a full lock rather than a directional freeze.

    PermissionedDEX use case (XLS-81): Allows creating Permissioned DEXes — restricted order books where only accounts that belong to a PermissionedDomain can place or accept offers. Enables compliant on-chain trading environments for regulated securities.

    Price Oracles

    Feature Introduced Mainnet Status Activated
    PriceOracle v2.2.0 ✅ Active 2024-11-02

    PriceOracle use case (XLS-47): Adds the Oracle ledger entry type and OracleSet/OracleDelete transactions. Authorized oracle providers publish price data for asset pairs (e.g., XRP/USD) directly on-ledger. Consumers read the data with get_aggregate_price and must validate the LastUpdateTime against an acceptable staleness threshold. Designed for DeFi applications that need on-chain price references without requiring a third-party oracle bridge.

    Identity and Compliance

    Feature Introduced Mainnet Status Activated
    DID v2.0.0 ✅ Active 2024-10-30
    Credentials v2.3.0 ✅ Active 2025-09-04
    PermissionedDomains v2.4.0 ✅ Active 2026-02-04

    DID use case (XLS-40): Anchors a W3C Decentralized Identifier document on-ledger (DIDSet/DIDDelete). The DID ledger entry stores a URI pointing to the DID document and an optional document hash for integrity. Enables self-sovereign identity attestations and Verifiable Credential anchors without a central registry.

    Credentials use case (XLS-70): Adds Credential ledger entries — a verifiable credential issued by one account to another (CredentialCreate, CredentialAccept, CredentialDelete). Credentials can be required for DepositPreauth and, through the now-active PermissionedDomains, for access-gated features like PermissionedDEX; LendingProtocol will use the same mechanism once it activates. An accepted credential is stored on the subject's account; the issuer can revoke it by deleting it.

    PermissionedDomains use case (XLS-80): Creates PermissionedDomain ledger entries that reference a set of Credentials. Accounts must hold a valid credential from the domain's accepted issuers to participate in domain-restricted operations (PermissionedDEX, LendingProtocol). The domain owner manages the credential issuer list via PermissionedDomainSet.

    Cross-Chain Bridges

    Feature Introduced Mainnet Status Activated
    XChainBridge v2.0.0 🗳️ Voting —

    XChainBridge use case (XLS-38): Adds a cross-chain bridge protocol allowing asset transfers between the XRPL Mainnet and sidechains. A Bridge ledger object defines the locking-chain and issuing-chain accounts. Witness servers attest to cross-chain events. Eight new transaction types (XChainCreateBridge, XChainCommit, XChainClaim, etc.) orchestrate the transfer.     Lending Protocol and Vaults

    Feature Introduced Mainnet Status Activated
    SingleAssetVault v3.1.0 🗳️ Voting —
    LendingProtocol v3.1.0 🗳️ Voting —
    LendingProtocolV1_1 v3.3.0 🔧 Dev —

    SingleAssetVault use case (XLS-65): Introduces Vault ledger objects — pools where multiple depositors aggregate a single asset. Vault depositors receive share tokens representing their proportional ownership. New transactions: VaultCreate, VaultSet, VaultDelete, VaultDeposit, VaultWithdraw, VaultClawback.     LendingProtocolV1_1 note: Currently Supported::No — still in development. Represents the next iteration of the lending protocol. Not votable in xrpld 3.3; available only on private test networks.

    Permission Delegation

    Feature Introduced Mainnet Status Notes
    PermissionDelegation v2.5.0 ⚠️ Obsolete (v2.6.1) Bug: disabled
    PermissionDelegationV1_1 v3.x 🗳️ Voting Replacement

    PermissionDelegationV1_1 use case (XLS-75): Allows an account (delegator) to authorize another account (delegate) to sign specific transaction types on its behalf using a DelegateSet transaction. The Delegate ledger entry records the permissions granted (e.g., allow Payment and OfferCreate but not AccountSet). Transactions signed by the delegate include the delegator's account in a Delegate field. Enables operational separation: a hot wallet signs routine transactions; a cold wallet holds the account without daily signing risk.

    Historical note: The original PermissionDelegation amendment (v2.5.0) was disabled in v2.6.1 due to a bug. It is listed as Obsolete in the source. Do not rely on it. PermissionDelegationV1_1 is the correct implementation.

    Batch Transactions

    Feature Introduced Mainnet Status Notes
    Batch (original) v2.5.0 ⚠️ Obsolete (v3.1.1) Security bug
    BatchV1_1 v3.3.0 🗳️ Voting Replacement

    BatchV1_1 use case: Allows submitting up to 8 inner transactions atomically in a single outer Batch transaction. The outer transaction is signed by the fee payer; inner transactions can be signed by different accounts (tfAllSigners mode) or just the outer signer (tfOuterSigner mode). All inner transactions succeed or all fail — true atomicity. Enables: atomic multi-asset swaps, token issuance + trust line setup in one round-trip, multi-step DeFi operations without partial-execution risk.

    Historical note: The original Batch amendment (v2.5.0) was obsoleted in v3.1.1 due to the fixBatchInnerSigs security issue. BatchV1_1 is the correct implementation. Any reference to the original Batch amendment ID should be treated as dead.

    Confidential Transfers

    Feature Introduced Mainnet Status Notes
    ConfidentialTransfer v3.3.0 🗳️ Voting —

    ConfidentialTransfer use case: Adds encrypted MPT transfers using zero-knowledge proofs. New transactions: ConfidentialMPTConvert (converts public MPT balance into a confidential balance), ConfidentialMPTSend (transfers between confidential balances), ConfidentialMPTConvertBack (returns to public balance), ConfidentialMPTMergeInbox (merges received confidential transfers into one's balance), ConfidentialMPTClawback (issuer clawback of confidential balances). Enables privacy-preserving stablecoin and token transfers on-ledger. Requires MPTokensV1.

    The confidential balance is stored as an encrypted ciphertext. Only the holder and the issuer (for clawback) can decrypt amounts. Validators verify correctness via ZK proofs without seeing values. Designed for regulated financial institutions needing transaction confidentiality.

    Sponsorship

    Feature Introduced Mainnet Status Notes
    Sponsor v3.3.0 🔧 Dev In development

    Sponsor use case (XLS-68, in development): Allows sponsors (companies, issuers) to cover transaction fees and reserve requirements for end users. Two new transactions: SponsorshipSet (sponsor pre-authorizes covering costs for a sponsee) and SponsorshipTransfer (executes the sponsored transfer). The sponsee retains full key control; the sponsor pays. Lowers onboarding friction: users can receive and send tokens without holding XRP for fees or reserves. Currently Supported::No — not votable in xrpld 3.3.

    Example flow: checking amendment readiness before building

    1. Check mainnet status:   GET /server_info → look at "amendments" array
2. Check voting progress:  GET /feature → inspect "vote" and "threshold"
3. Test on Devnet:         Deploy with amendment enabled on private chain
4. Monitor activation:     Alert when amendment support > 70% for 1 week
5. Plan upgrade:           Ensure xrpld ≥ minimum version before activation

    Worked example: activating an amendment on a private network

    The public networks make you wait two weeks after an amendment reaches 80% support (kDefaultAmendmentMajorityTime = weeks{2} in SystemParameters.h). On a standalone network you are the sole validator, so you can force an amendment through the entire lifecycle — from voting to activation — in minutes. This is the definitive way to test that your code behaves correctly both before and after a feature turns on.

    The three levers, all confirmed against source:

    • [amendment_majority_time] — the config stanza (kAmendmentMajorityTime in Constants.h, parsed in Config.cpp) that shortens the majority-hold window. It accepts minutes|hours|days|weeks with a 15-minute minimum (amendmentMajorityTime < minutes(15) is rejected). Set it low so you do not wait two weeks.
    • [amendments] / [veto_amendments] — the config lists (kAmendments / kVetoAmendments) of amendment IDs this node up-votes / down-votes.
    • ledger_accept — the standalone-only RPC that closes and validates the open ledger on demand (handler LedgerAccept.cpp), advancing you toward and across the flag ledger.

    Goal: take a chosen amendment from voting to enabled on a private net.

    1. Configure the node. In your standalone xrpld.cfg, add the amendment to the up-vote list and shrink the majority window:
    [amendment_majority_time]
15 minutes

[amendments]
<amendment_id>    <AmendmentName>
    1. Start standalone from a fresh ledger.
    xrpld -a --start
    1. Confirm the starting state. Query the feature RPC — with no argument it returns the full amendment table (doFeature in Feature.cpp). The chosen amendment should show "enabled": false and, initially, no majority.
    xrpld feature <AmendmentName>
    1. Advance to a flag ledger. Amendment votes are only tallied on flag ledgers (index divisible by 256). Call ledger_accept repeatedly to close ledgers until you cross one; the validator (you) votes yes because the amendment is in [amendments].
    xrpld ledger_accept   # repeat until past a flag ledger

    1. Watch the majority appear. After the flag ledger, feature <name> will report a majority timestamp — the moment your (100%) support was recorded. The two-week clock is now your 15 minutes.

    2. Cross the majority window. Wait out the shortened amendment_majority_time, then advance past the next flag ledger with more ledger_accept calls. The node injects the EnableAmendment (ttAMENDMENT) pseudo-transaction, and the amendment flips to "enabled": true.

    3. Verify activation both ways. server_info now lists the amendment in its active set, and transactions that previously returned temDISABLED now apply. Run your test suite against this node to confirm the enabled-path behavior.

    Non-obvious insight: you can also veto interactively without editing the config, using the admin feature RPC: feature <name> vetoed=true calls table.veto(...) and vetoed=false calls unVeto(...) (Feature.cpp, admin-only). This lets you flip a single node's vote mid-session — useful for simulating a validator that changes its mind — but the durable, reproducible way to seed votes is the [amendments]/[veto_amendments] config lists.

    Watch out: the 15-minute floor is real. Setting amendment_majority_time below it makes xrpld refuse to start. If you want instant activation for a pure enabled-vs-disabled behavioral test (and do not care about exercising the voting mechanism itself), the simpler path is to run a network where the amendment is already active and focus the test on transaction behavior.

    Security considerations

    • Do not gate production flows on an unactivated amendment. A feature open for voting may not activate for months — or may stall indefinitely.
    • Obsolete amendments are a dead end. Code referencing PermissionDelegation or the original Batch amendment IDs will never execute on mainnet.
    • Supported::No features are devnet-only. MPTokensV2, LendingProtocolV1_1, and Sponsor are not votable in any released xrpld version and must not appear in mainnet architecture plans.
    • Amendment-blocking is silent without monitoring. A node becomes amendment-blocked without crashing. Monitor amendment_blocked in server_info on every production node.

    Common mistakes

    • Building on a feature before it activates. Check server_info.amendments — not documentation — to confirm an amendment is live on the chain you are connecting to.
    • Confusing Devnet with Mainnet activation. Devnet runs with many amendments force-enabled. Code tested on Devnet may rely on amendments that are still voting on Mainnet.
    • Treating obsolete amendments as live. The original Batch and PermissionDelegation hashes will never appear in a future mainnet Amendments ledger entry; they exist only in the source's obsolete list.
    • Not pinning minimum xrpld version. Infrastructure that allows any xrpld version may connect to a node that does not support a required amendment. Always enforce a minimum version compatible with your feature set.
    • Using MPTokensV2 in production architecture. It is Supported::No in xrpld 3.3 — the server cannot vote for it and does not enable it on mainnet.

    What I learned

    • Amendments are governance encoded as protocol, not tooling. The two-week majority hold (kDefaultAmendmentMajorityTime = weeks{2}) is a deliberate social buffer: it gives operators time to upgrade before a rule changes, which is the whole point of on-ledger amendments versus disruptive hard forks.
    • The activation clock is configurable, but only on your own network. [amendment_majority_time] lets a private net compress two weeks into 15 minutes — the minimum the code enforces. You cannot shorten it on Mainnet; there the buffer is a feature, not an inconvenience.
    • Votes only count on flag ledgers. Nothing about an amendment's status changes between flag ledgers (indices divisible by 256). In standalone this is concrete: you ledger_accept your way to a flag ledger before a vote is even tallied, which makes the otherwise-invisible cadence tangible.
    • "Not activated" fails loudly and early. Submitting a transaction for a disabled amendment returns temDISABLED — a malformed-class code rejected before it can claim a fee. So building against an unactivated feature fails safe (free, off-ledger) rather than silently succeeding, which is why testing the disabled path is as important as testing the enabled one.
    • Standalone mode is the only place you can watch the full lifecycle. On a public network you observe activation; in standalone you drive it — vote, cross the flag ledger, wait out the (shortened) window, and see the EnableAmendment pseudo-transaction flip the feature on.
