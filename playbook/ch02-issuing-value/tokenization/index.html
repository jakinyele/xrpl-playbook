    Tokenization

    Why does this matter?

    Tokenizing a real-world asset is not just minting a token — it is encoding an asset's legal rights, transfer restrictions, and lifecycle events into a programmable ledger object. The choice of primitive (issued currency, MPT, or NFT) has permanent consequences for the asset's behavior, compliance posture, and secondary market liquidity. Choose wrong and you'll be redeeming and re-issuing under pressure.

    Mental model

    Choose the smallest primitive that fully satisfies the asset's requirements:

    • Issued currencies — fungible, highly liquid, deep DEX/AMM integration. Best for high-volume homogeneous assets (stablecoins, commodities).
    • Multi-Purpose Tokens (MPTs) — fungible tokens with richer on-ledger metadata and lifecycle controls; lower reserve overhead than trust lines at scale. Best for regulated securities and structured products.
    • NFTs (XLS-20) — non-fungible; each token is unique. Best for assets where individual provenance matters (real estate, art, loans).

    The key question is fungibility: are all units of this asset economically interchangeable? If yes, use MPT or issued currency. If no, use NFT.

    Architecture

    • Asset onboarding — off-ledger legal wrapper, on-ledger token configuration, metadata anchoring.
    • Holder management — authorized trust lines (issued currency / MPT) or transfer restrictions (NFT) tied to KYC/AML verification.
    • Lifecycle events — corporate actions (dividends, splits), maturity, redemption, and burning.
    • Metadata — on-ledger URI plus off-ledger verifiable document; integrity anchored via content hash in the token URI field.

    Example flow

    Issuing a permissioned, transferable MPT

    This traces a regulated (allowlisted) Multi-Purpose Token from configuration through holder onboarding to a restricted secondary transfer. On a classic (pre-DynamicMPT) issuance the capability flags are fixed at creation — you cannot add Clawback, Transfer, or RequireAuth to an existing issuance (contrast the account-level flags in Issuer Controls), so the design decision is made once, up front. The DynamicMPT amendment relaxes this only for capabilities you explicitly pre-declare mutable at creation via MutableFlags (see the note at the end of this flow).

    1. Create the issuance. The issuer submits MPTokenIssuanceCreate with the capability flags baked in:
    2. tfMPTRequireAuth — every holder must be explicitly authorized before they can receive units (the allowlist gate).
    3. tfMPTCanTransfer — permits holder-to-holder (secondary) transfers. Without it, units can only move to and from the issuer.
    4. tfMPTCanClawback / tfMPTCanLock — reserve the right to repossess or freeze balances for compliance.

    Optional configuration set here: MaximumAmount (hard supply cap, ≤ kMaxMpTokenAmount = 2⁶³−1), AssetScale (decimal places), TransferFee (≤ kMaxTransferFee = 50000, i.e. 50%, and only valid when tfMPTCanTransfer is set), and MPTokenMetadata (≤ kMaxMpTokenMetadataLength = 1024 bytes). MaximumAmount and AssetScale are permanently immutable; TransferFee and MPTokenMetadata are immutable too unless you opt into mutability at creation with the matching MutableFlags bit (DynamicMPT). The transaction returns a deterministic MPTokenIssuanceID derived from the issuer account and sequence — the stable handle every later step references.

    1. Holder opts in. The prospective holder submits MPTokenAuthorize naming the MPTokenIssuanceID (and no Holder field). This creates the holder's MPToken object with a zero balance. The issuer cannot create this object on the holder's behalf — the holder must opt in first (preclaim in MPTokenAuthorize.cpp requires the MPToken to exist before the issuer can authorize it). An issuer also cannot authorize itself: holding your own issuance returns tecNO_PERMISSION.

    2. Issuer authorizes the holder. Because lsfMPTRequireAuth is set, the issuer submits MPTokenAuthorize with the Holder field to flip the holder's lsfMPTAuthorized flag. Skipping the on-ledger RequireAuth flag makes this step a no-op — the transaction returns tecNO_AUTH, so an allowlist you never enabled provides no enforcement.

    3. Primary issuance. The issuer sends units to the authorized holder via Payment. This raises sfOutstandingAmount on the issuance (the MPT analogue of total supply), capped by MaximumAmount if one was set.

    4. Restricted secondary transfer. Holder A pays Holder B. This succeeds only because tfMPTCanTransfer was set at creation and Holder B is already authorized. If a TransferFee was configured, it is deducted here — analogous to TransferRate on an issued currency, but encoded on the issuance object rather than the account.

    5. Compliance action (optional). To halt a specific holder, the issuer submits MPTokenIssuanceSet with tfMPTLock (requires lsfMPTCanLock), setting lsfMPTLocked on that holder's MPToken; tfMPTUnlock reverses it. To repossess, the issuer submits a Clawback naming the Holder (requires lsfMPTCanClawback), reducing the holder's balance and sfOutstandingAmount together.

    The through-line: on an MPT, policy is decided at creation and enforced per-holder thereafter. There is no AccountSet-style free retrofit: a capability is available later only if it (or the right to enable it) was declared at creation. Concretely, with DynamicMPT an issuer may pre-authorize future changes by setting MutableFlags bits (tmfMPTCanEnableCanTransfer, tmfMPTCanMutateTransferFee, tmfMPTCanMutateMetadata, etc.); a later MPTokenIssuanceSet can then flip only those pre-blessed capabilities. Anything not pre-declared mutable — and MaximumAmount/AssetScale in all cases — is permanently fixed.

    DynamicMPT lifecycle — deferring policy decisions

    The DynamicMPT amendment (voting as of xrpld 3.4; Supported::Yes, DefaultNo in features.macro) enables issuers to defer specific policy decisions by pre-declaring capabilities as mutable at creation time. This is controlled, opt-in evolution — not a free-form retrofit.

    Amendment gate: requires featureDynamicMPT active on the network; any MPTokenIssuanceCreate with sfMutableFlags returns temDISABLED without it.

    Source: rippled/src/libxrpl/tx/transactors/token/MPTokenIssuanceCreate.cpp (line 38)

    Phase 1: Creation with mutability pre-declarations

    Submit MPTokenIssuanceCreate with sfMutableFlags encoding which capabilities the issuer reserves the right to enable later:

    sfMutableFlags bit Allows future enable of Ledger flag enabled
    tmfMPTCanEnableCanLock lsfMPTCanLock Per-holder lock capability
    tmfMPTCanEnableRequireAuth lsfMPTRequireAuth Holder authorization requirement
    tmfMPTCanEnableCanEscrow lsfMPTCanEscrow Escrow support
    tmfMPTCanEnableCanTrade lsfMPTCanTrade DEX trading
    tmfMPTCanEnableCanTransfer lsfMPTCanTransfer Holder-to-holder transfers
    tmfMPTCanEnableCanClawback lsfMPTCanClawback Issuer clawback
    tmfMPTCanMutateMetadata — Allows MPTokenMetadata updates
    tmfMPTCanMutateTransferFee — Allows TransferFee changes

    Source: rippled/include/xrpl/protocol/TxFlags.h (lines 359–390), rippled/include/xrpl/protocol/LedgerFormats.h (lines 183–207).

    Example: an issuer launching a bond token may want to defer the transfer capability decision pending regulatory approval: 

    {
  "TransactionType": "MPTokenIssuanceCreate",
  "Account": "<issuer>",
  "MaximumAmount": "1000000000",
  "AssetScale": 2,
  "Flags": 0,
  "MutableFlags": 32
}
    MutableFlags=32 is tmfMPTCanEnableCanTransfer — the issuer does not enable transfers now but reserves the right to do so later.

    Phase 2: Enabling a pre-declared capability

    Once the regulatory green-light arrives, the issuer submits MPTokenIssuanceSet with the corresponding sfMutableFlags bit:

    {
  "TransactionType": "MPTokenIssuanceSet",
  "Account": "<issuer>",
  "MPTokenIssuanceID": "<issuance_id>",
  "MutableFlags": 16
}
    MutableFlags=16 is tmfMPTSetCanTransfer — this flips lsfMPTCanTransfer to enabled. Holders can now transfer among themselves.

    Source: rippled/src/libxrpl/tx/transactors/token/MPTokenIssuanceSet.cpp (lines 51–69, kMptMutabilityFlags mapping table).

    Key constraints (source-verified)

    1. One-way enablement. Once a capability is enabled via MPTokenIssuanceSet, it cannot be disabled. The MPTokenIssuanceSet has no "remove capability" path — only tfMPTLock/tfMPTUnlock for per-holder operations.

    2. Permanently immutable fields.

    3. MaximumAmount — hard cap, set once, never changed.

    4. AssetScale — decimal precision, set once, never changed. These are not subject to DynamicMPT mutability regardless of what sfMutableFlags bits are set.

    5. Pre-declaration required. If tmfMPTCanEnableCanTransfer was NOT set in sfMutableFlags at creation, a later MPTokenIssuanceSet with tmfMPTSetCanTransfer returns tecNO_PERMISSION.

    6. Confidential balance exclusivity. If lsfMPTCanHoldConfidentialBalance is enabled, TransferFee > 0 cannot coexist (encrypted amounts make fee computation impossible). Source: MPTokenIssuanceSet.cpp line 88.

    Security considerations

    • Clawback and freeze posture (see Issuer Controls) must match the asset's legal offering documents.
    • MPT MaximumAmount is set at creation and cannot be changed.
    • Authorized minter accounts for NFTs should use multi-signing.

    Common mistakes

    • Choosing NFTs for fungible assets. Non-fungible tokens cannot be aggregated or routed through the DEX; fungible assets need fungible primitives.
    • Mutable metadata. Using a centrally-controlled URL as the token URI allows silent modification of the asset record after issuance.
    • Missing transfer restrictions. Regulated assets require on-ledger enforcement — RequireAuth and authorized trust lines — not just off-ledger policy.
    • Not modeling MPT reserve costs. MPT holder entries still consume ledger objects; plan reserve requirements for large holder sets.

    Production checklist

    • [ ] Token primitive chosen based on fungibility and compliance needs.
    • [ ] Metadata points to content-addressed or hash-verified storage.
    • [ ] Transfer restrictions are enforced on-ledger, not just in policy.
    • [ ] Authorized minter accounts use multi-signing.
    • [ ] MaximumAmount is capacity-planned before MPT deployment.
    • [ ] Lifecycle events (maturity, redemption, clawback) are scripted and tested before issuance.
    • [ ] On-ledger token state is reconciled with the off-ledger asset register on a defined schedule.

    This checklist covers tokenization. Before production, also complete the account-security checklist in ch04-hardening/security and the node-operations checklist in ch04-hardening/operations.

    What I learned

    • MPT capabilities are decided at creation. Unlike issued currencies, where account flags (RequireAuth, freeze, clawback) can be toggled on the issuer over its lifetime, an MPT's Transfer/Clawback/Lock/RequireAuth capabilities are set in MPTokenIssuanceCreate. On a classic issuance they are frozen for good; with DynamicMPT an issuer can change only the specific capabilities it pre-declared mutable (via MutableFlags) at creation. MaximumAmount and AssetScale are immutable in every case. The design decision is effectively permanent — plan it before the first transaction.
    • Authorization is a two-party handshake. With RequireAuth, the holder must create their MPToken object first (opt in), and only then can the issuer authorize it. The issuer can never conjure a balance on an account that has not opted in — a meaningful contrast to some allowlist models.
    • A capability flag you forgot to set fails silent-ish. Authorizing a holder on an issuance without RequireAuth returns tecNO_AUTH; a non-transferable MPT simply rejects secondary transfers. The absence of a flag is enforced as a hard tec/tem rejection, not a warning — so an incomplete configuration surfaces as failed transactions, not silent weakening of your controls.
    • Supply is sfOutstandingAmount, bounded by MaximumAmount. There is no separate "mint" primitive: issuing is a Payment from the issuer that raises outstanding amount, and clawback/redemption lowers it. If you cap supply, cap it at creation — MaximumAmount is immutable and bounded by 2⁶³−1.

    Open questions

    When should a developer choose Multi-Purpose Tokens (MPTs) over standard issued currencies?

    Choose an MPT when you need per-issuance policy and metadata baked into the token itself, and an issued currency when you need maximum liquidity and the deepest DEX/AMM/pathfinding integration. The distinction is structural, not cosmetic:

    • Holder-side reserve and object model. An issued-currency balance lives in a bidirectional RippleState (trust line) that both parties can be charged an owner reserve for and that carries NoRipple/freeze/limit state on each side. An MPT balance lives in a single MPToken object owned by the holder, pointing at one shared MPTokenIssuance. For issuers with large holder sets, the MPT model is simpler to reason about and the policy lives in one place (the issuance) rather than being negotiated per trust line.
    • Policy is first-class on an MPT. Capabilities (CanTransfer, CanClawback, CanLock, RequireAuth, CanEscrow, CanTrade), an optional hard supply cap (MaximumAmount), AssetScale, on-ledger MPTokenMetadata (≤ 1024 bytes), and a DomainID binding are all attributes of the issuance object. With issued currencies the equivalent controls are spread across account flags (AccountSet) and per-trust-line flags (TrustSet).
    • The trade-off is liquidity and maturity. Issued currencies are the older, universally-supported primitive with the richest tooling and market depth. MPTokensV1 is active but the surrounding ecosystem (AMM support via MPTokensV2, dynamic mutation via DynamicMPT) is still maturing. For a stablecoin that must trade everywhere today, issued currency is the safe default; for a regulated security or structured product where controls and compact per-holder state matter more than DEX ubiquity, MPT fits better.

    Confirmed against source — MPT capability flags and DomainID/MaximumAmount/ AssetScale/MPTokenMetadata fields in MPTokenIssuanceCreate.cpp; the single-MPToken-per-holder model in MPTokenAuthorize.cpp.

    How are decentralized identifiers and verifiable credentials integrated into the asset lifecycle?

    XRPL exposes three native, composable identity primitives, and they attach to tokens through permissioned domains rather than living inside the token object:

    • DID (ltDID) — one per account, an on-ledger anchor holding a DIDDocument, URI, and/or Data (all optional). It identifies who an account is (e.g. a KYC'd institution) in a W3C-DID-compatible way, but does not itself gate anything.
    • Credential (ltCREDENTIAL) — an attestation by an issuer about a subject: required Subject, Issuer, CredentialType, plus optional Expiration and URI. Created with CredentialCreate and made effective when the subject runs CredentialAccept — a two-party handshake mirroring MPT authorization. This is the verifiable-credential equivalent ("this account has passed accredited-investor KYC").
    • PermissionedDomain (ltPERMISSIONED_DOMAIN) — an AcceptedCredentials allowlist (credential type + issuer pairs). It answers "which credentials grant entry to this compliance perimeter?"

    The lifecycle linkage: an issuer creates a domain listing the credential types it trusts, then binds a token to it. An MPT issuance carries a DomainID (which requires tfMPTRequireAuth), and PermissionedDEX restricts order books to domain members. The result is credential-gated access enforced on-ledger: only accounts holding an accepted, unexpired credential can hold or trade the asset — without the issuer manually authorizing each holder.

    Confirmed against source — object fields in ledger_entries/{DID,Credential,PermissionedDomain}.h; credential handshake in CredentialCreate.cpp / CredentialAccept.cpp; DomainID-requires-RequireAuth in MPTokenIssuanceCreate.cpp.

    What does the end-to-end lifecycle of a Real-World Asset (RWA) look like on-ledger?

    A representative regulated-RWA lifecycle, composing the primitives above:

    1. Identity & compliance setup. The issuer establishes its own DID, then stands up a PermissionedDomain whose AcceptedCredentials name the KYC/accreditation credential types (and trusted credential issuers) required to hold the asset.
    2. Investor onboarding. A credential issuer runs CredentialCreate for the investor; the investor CredentialAccepts it. The investor now satisfies the domain without any bespoke per-investor issuer action.
    3. Asset issuance. The issuer runs MPTokenIssuanceCreate with tfMPTRequireAuth + a DomainID, capabilities matching the offering docs (CanTransfer, CanClawback, CanLock), a MaximumAmount cap, and MPTokenMetadata anchoring the legal wrapper (hash of the offering document).
    4. Primary distribution. Domain-member investors opt in (MPTokenAuthorize), then receive units by Payment, raising sfOutstandingAmount.
    5. Secondary market. Members trade on a PermissionedDEX order book scoped to the domain; a configured TransferFee accrues to the issuer on each transfer.
    6. Corporate actions & lifecycle events. Coupons/dividends are paid as separate payments; freezes use MPTokenIssuanceSet (tfMPTLock) per holder; compliance recovery uses Clawback.
    7. Maturity / redemption / retirement. Holders return units to the issuer (lowering sfOutstandingAmount); once fully redeemed the issuer can MPTokenIssuanceDestroy, and expired credentials naturally drop investors from the domain.

    Educated guess (not directly encoded in source): the ordering above (identity → domain → credentials → issuance) is a design recommendation, not a protocol-enforced sequence. The protocol enforces the individual dependencies (a DomainID requires RequireAuth; a domain must exist before it is referenced; a holder must opt in before authorization), but composing them into this end-to-end flow is an application-level pattern.
