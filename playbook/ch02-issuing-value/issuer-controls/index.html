    Issuer Controls

    Mechanisms for enforcing regulatory compliance, managing risk, and maintaining token integrity through protocol-level account and object flags.

    Why does this matter?

    On a public, decentralized ledger, issuers are often legally or operationally responsible for the tokens they issue. Without protocol-level controls, an issuer cannot: - Block sanctioned actors from holding their tokens. - Recover funds sent to a lost or compromised account (Clawback). - Halt trading during a security incident (Global Freeze). - Signal immutability to users to build trust (NoFreeze).

    Mental model

    Issuer controls exist at two distinct layers:

    1. Account-level flags (The Policy): Set once on the issuer's account root to define the rules for all tokens issued by that account.
    2. Object-level flags (The Enforcement): Set on specific trust lines (IOUs) or token issuances (MPTs) to enforce policies on a per-holder basis.
    Control Type Account Flag (Policy) Object Flag (Enforcement)
    Authorization asfRequireAuth tfSetfAuth (TrustSet) / MPTokenAuthorize
    Freezing asfGlobalFreeze tfSetFreeze (TrustSet) / tfMPTLock
    Clawback asfAllowTrustLineClawback Clawback transaction
    Immutability asfNoFreeze n/a (Account-wide permanent lock)

    Architecture

    The tecOWNERS Gate

    The most critical architectural constraint in the XRPL is that fundamental policy flags (RequireAuth and AllowTrustLineClawback) can only be enabled when the issuer account's owner directory is empty.

    Consequence: You must configure your issuer account before issuing a single token, creating an offer, or setting up a signer list. Retroactive enforcement is impossible without migrating to a new issuer account.

    Trust Line (IOU) vs. MPT Controls

    • Trust Lines: Use AccountSet for policy and TrustSet for per-holder enforcement.
    • MPTs: Use MPTokenIssuanceCreate to define capabilities (sfMutableFlags) and MPTokenIssuanceSet to toggle them. MPTs do not use AccountSet for most controls.

    Example flow: Clawing back funds

    The Clawback transaction was introduced via amendment to allow issuers to repossess tokens (e.g., for legal compliance or fraud recovery).

    1. Setup: Issuer sets asfAllowTrustLineClawback via AccountSet (while owner count is 0).
    2. Issuance: Issuer sends tokens to a holder.
    3. Trigger: A recovery event occurs.
    4. Transaction: Issuer submits a Clawback transaction.
      • Trust Line: sfAmount's issuer is the holder's account.
      • MPT: sfHolder specifies the account to claw back from.
    5. Result: Balance is deducted from the holder and credited back to (or burned by) the issuer.

    Try it yourself

    Using the Testnet faucet at https://xrpl.org/resources/dev-tools/xrp-faucets:

    1. Set asfNoFreeze on a test issuer account, then attempt to set asfGlobalFreeze. What result code do you get? Is the fee charged?
    2. Enable asfRequireAuth on the issuer, then have a second account attempt to create a trust line and receive tokens without authorization. What happens?
    3. Attempt asfAllowTrustLineClawback without first enabling it. What happens if the flag is not set and you submit a Clawback transaction?
    4. Set a TransferRate of 1,005,000,000 (0.5% fee). Send 100 USD between two non-issuer accounts. How much does the recipient receive? How much goes to the issuer?
    5. Set asfGlobalFreeze, verify the state via account_info Flags field, then attempt a peer-to-peer transfer. What result code is returned?

    Security considerations

    • asfNoFreeze is permanent. Once enabled, the issuer can never freeze tokens again. This is used to signal "permissionless" status to the market but is a massive liability if the token is regulated.
    • Master Key requirement. Setting asfNoFreeze requires signing with the Master Key (if not disabled). This prevents a secondary "regular key" from accidentally or maliciously revoking the issuer's control.
    • Clawback is a "trust me" feature. Exchanges and DeFi protocols often flag tokens with clawback enabled as higher risk, as the issuer can unilaterally remove liquidity.

    Common mistakes

    • Enabling DefaultRipple before RequireAuth. On a regulated token, this creates a window where anyone can create a trust line and receive tokens via rippling before you can authorize them.
    • Forgetting tecOWNERS. Trying to enable Clawback or RequireAuth after the account is already operational. This usually results in a failed deployment.
    • Misunderstanding NoFreeze. Thinking it only applies to new trust lines. It actually prevents the issuer from clearing an existing GlobalFreeze as well.

    Production checklist

    • [ ] Issuer account configured with RequireAuth before any tokens issued.
    • [ ] AllowTrustLineClawback set if regulatory recovery is required.
    • [ ] DefaultRipple enabled ONLY if cross-issuer rippling is intended.
    • [ ] Cold wallet master key used to set NoFreeze (if applicable).
    • [ ] Holder authorization workflow (KYC -> tfSetfAuth) automated.

    This checklist covers issuer controls. Before production, also complete the account-security checklist in ch04-hardening/security and the node-operations checklist in ch04-hardening/operations.

    What I learned

    The tecOWNERS constraint is the "Original Sin" of XRPL issuance. It enforces a strict "Config-then-Operate" lifecycle. If you forget to set RequireAuth at T-0, your token is effectively permissionless forever on that account.

    Open questions

    • DeepFreeze (active since v2.4.0, 2025-05-04): how does it interact with AMMs — can a deep-frozen balance be used as liquidity?
    • MPT Global Freeze: Is there a single-transaction equivalent to GlobalFreeze for an MPT issuance, or must every holder be locked individually?
